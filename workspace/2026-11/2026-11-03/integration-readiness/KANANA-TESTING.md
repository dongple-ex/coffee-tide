# Kanana 실서버 추가 측정 준비

- 기준일: 2026-11-03 (Asia/Seoul)
- 사용자 관찰: 서버 성능 제약이 있고 실사용 응답이 느림.
- 이번 판정: 성능·품질 추가 검증 전까지 시험 제공자로 유지한다. Gemini 기본 경로를 바꾸지 않는다.
- 실제 서버 주소·키는 로컬에 없으므로 이번 작업에서 실서버 추론을 수행하지 않았다.

## 준비된 측정

기존 어댑터 테스트는 실제 모델을 대신하는 HTTP 시험 응답으로 인증·문맥 제한·타임아웃·오류 처리를 검사한다. 실서버 속도를 나타내지 않는다. 추가 도구 kanana-benchmark.mjs는 실제 모델 측정을 담당자가 실행할 수 있도록 준비했다.

| 항목 | 범위 |
|---|---|
| 입력 | 인사·가상 업무 요약·가상 회의 근거 질문만 사용 |
| 실행 | 기본 외부 요청 0회, --run 지정 시 1~6개 순차 요청 |
| 출력 제한 | 기본 64토큰, 32~256토큰 범위 |
| 측정 | HTTP 헤더 응답까지 걸린 시간, 요청 전체 시간, 성공·실패·중단 여부 |
| 응답 보관 | 원문·질문·서버 주소·인증값을 결과에 넣지 않음 |
| 통계 | 소수 표본의 성공 응답 중앙값·95백분위. 부하 시험이나 운영 적합성 판정 아님 |
| 품질 | 답변 문장 수·길이·출력 잘림 여부만 기록. 사실 정확성과 한국어 품질은 별도 확인 |

## 실행

기존 환경변수 KANANA_API_URL, KANANA_API_KEY, KANANA_MODEL, KANANA_TIMEOUT_MS를 안전하게 주입한 환경에서 실행한다. 명령 인수에 주소·키를 넣지 않는다.

```powershell
node workspace/2026-11/2026-11-03/integration-readiness/kanana-benchmark.mjs
```

위 명령은 설정 존재 여부와 계획만 표시한다. 실제 시험을 담당자가 수행할 때만 다음 명령을 사용한다.

```powershell
node workspace/2026-11/2026-11-03/integration-readiness/kanana-benchmark.mjs --run --samples=6 --max-tokens=64
```

실제 서버는 HTTPS가 필요하다. 첫 요청과 반복 요청을 구분해 기록하고 동일한 출력 제한으로 비교한다. 위 6개 요청은 같은 3종류 질문을 두 번씩 실행한다. 기본 120초 제한은 대기 상한이며 생성 속도를 개선하지 않는다. 응답은 stream=false이므로 첫 토큰 지연은 측정하지 않는다.

## 실사용 전 판단

| 확인할 항목 | 남길 근거 |
|---|---|
| 서버 | CPU·RAM·GPU 사용 여부, 모델 정밀도·양자화, 추론 엔진, 스레드 수 |
| 지연 | 첫 요청·반복 요청의 전체 시간과 타임아웃 비율 |
| 생성량 | 동일 입력과 32·64·128토큰 제한별 결과 |
| 동시성 | 초기에는 1건씩 실행. 실제 대기·429·503 처리 확인 |
| 품질 | 한국어 답변·자료 근거·없는 사실을 추가하는지 확인 |
| 기준 | 사용자가 수용할 응답 대기 시간과 품질 기준을 먼저 정하고 결과와 비교 |

이번 도구는 의도적으로 productionReady=false를 유지한다. 소수 표본의 API 응답만으로 실사용 전환을 결정하지 않는다. 시험 중 COPILOT_AI_PROVIDER를 바꾸지 않으며, Telegram 초기 연동은 Gemini 기본값으로 준비한다. 이후 제공자를 바꿀 경우 웹 Copilot과 Telegram의 공통 대화 경로에 함께 적용된다는 점을 확인한다.
