# 모바일 전략

> **2026-09-23 현황:** 현재 제공 기반은 반응형 웹과 Windows Electron 보조 앱입니다. iOS/Android WebView 래퍼·앱 스토어 출시는 후속 계획이며 현재 구현·출시 완료 상태가 아닙니다.
> 관련 문서: [`00-product-spec.md`](./00-product-spec.md)(정본 기획), [`phase6-llm-artifacts.md`](./spec/phase6-llm-artifacts.md) §13(데스크톱 전용 제약), [`02-backlog.md`](./02-backlog.md) E3(반응형 점검).

---

## 1. 기본 방침

1. **웹 코어 우선 (Web-Core First)**: `coffee-tide.dongple.kr`에서 동작하는 반응형 웹 앱을 핵심 엔진으로 사용합니다.
2. **하이브리드 앱 래퍼는 후속 선택지**: WebView 기반 래퍼는 출시 가이드의 제안이다. 현재 Windows Electron 보조 앱과는 별개이며, 모바일 웹의 핵심 흐름을 먼저 검증한다.
3. **모바일은 축소판이 아니라 "입력·확인 중심 뷰"**: 모바일에서는 업무를 빠르게 넣고(manual/paste), 브리핑을 확인하고, 완료 처리하는 흐름을 우선합니다.

## 2. 단계별 로드맵

| 단계 | 내용 | 2026-09-23 상태 |
| :--- | :--- | :--- |
| M1 | **반응형 웹** — 빠른 입력·바리스타 대화·페이지 내 독·캔버스·작업 복원 | 코드 구현, 기기별 검증 계속 |
| M2 | **하이브리드 앱 래퍼** — 네이티브 권한·푸시·로그인 연결 | 계획, 플랫폼 프로젝트·배포 증거 미확인 |
| M3 | **앱 스토어 출시** — 플랫폼별 심사·배포 | 미실행, M2 후 검토 |

## 3. 데스크톱 전용 기능의 모바일 처리

서버 파일시스템(`fs`) 연동은 서버가 해당 파일에 접근할 수 있어야 합니다. 클라우드 서버가 사용자 PC 폴더를 읽을 수는 없습니다. 지원 데스크톱 브라우저의 File System Access 폴더 연결은 별도 경로이며, 모바일 지원으로 일반화하지 않습니다.

| 기능 | 모바일 동작 | 처리 방침 |
| :--- | :--- | :--- |
| `manual` / `paste` 입력 | ✅ 가능 | 모바일의 **1순위 입력 경로**. 입력 폼을 모바일 최상단에 배치 |
| 개별 문서 업로드 | ✅ 가능 | OS 파일 선택기에서 파일 앱·클라우드 저장소의 문서를 선택해 서버에서 파싱. 파일 크기·형식 제한과 업로드 진행 상태 표시 |
| Copilot 브리핑, 완료/보류/삭제 | ✅ 코드 경로 제공 | 원본 쓰기는 연결·인증·소스별 지원 범위에 따름 |
| `outlook` / `notion` / `gmail` / `gcalendar` / `gdrive` | ✅ 코드 경로 제공 | OAuth·API·공급자 설정 및 실계정 검증 필요 |
| `local_doc` (로컬 문서 폴더) | ❌ 불가 | 연동 카드 숨김 + "데스크톱 전용" 안내 |
| `obsidian` (볼트 스캔·캡처·미러링) | ❌ 불가 | 연동 카드 숨김 + "데스크톱 전용" 안내 |
| `llm` (LLM 산출물 폴더 스캔) | ❌ 불가 | 연동 카드 숨김 + "데스크톱 전용" 안내 ([`phase6`](./spec/phase6-llm-artifacts.md) §13) |
| 네이티브 폴더 선택기 (`/api/util/select-folder`) | ❌ 불가 | 해당 기능 진입점 자체를 미노출. 개별 파일 업로드와 구분 |
| 등록형 로컬 스크립트 실행 | ⚠️ 조건부 | 클라우드 배포에서는 불가. 사용자 PC의 CoffeeTide에 같은 네트워크로 접속한 경우 PC에서 실행하고 모바일은 미리보기·승인·결과 확인만 담당 |
| Cloud Tool Registry | ✅ 가능 | 읽기·초안은 동일 API로 실행. Calendar·Drive 쓰기는 모바일 검토 카드와 별도 최종 승인 카드에서 도구·대상·계정·변경·만료를 확인한 뒤 44px 승인 버튼으로 1회 실행 |

판별 방식: User-Agent 스니핑보다 **배포 형태 기준**(§4)으로 기능을 게이팅하고, 화면 크기는 레이아웃에만 사용합니다.

## 4. 배포 형태와의 관계 (중요한 갈림길)

현재 설계는 Next.js 단일 앱이 로컬 파일까지 읽는 구조라, 배포 형태에 따라 기능 집합이 달라집니다.

- **셀프호스팅 (사용자 PC에서 실행)**: 운영체제·권한·인증이 충족된 기능을 제공. 로컬 파일 연동(local_doc/obsidian/llm) 포함. 같은 네트워크의 모바일 브라우저에서 접속하면 모바일에서도 로컬 연동 *결과*는 볼 수 있음.
- **클라우드 배포 (`coffee-tide.dongple.kr`)**: 로컬 파일 연동 3종과 로컬 스크립트 실행은 **비활성**. manual/paste, 개별 문서 업로드, 외부 API 연동(outlook/notion/gmail)은 제공.

→ 정본의 "무연동 우선(manual/paste 1급 소스)" 원칙(G1)이 지켜지면 클라우드 배포판도 그 자체로 완결된 제품이 됩니다. **모바일 전략의 성립 조건이 곧 G1 구현**입니다.

## 5. 모바일 UX 원칙

1. 첫 화면에서 "빠른 업무 추가" 입력이 엄지 도달 범위 안에 있어야 합니다.
2. 카드 액션(완료/보류/삭제)은 터치 타깃 44px 이상, 이모지 버튼에는 `aria-label` 필수 (백로그 E1).
3. 본문 클램프는 탭으로 펼침 (백로그 E2).
4. 30초 폴링은 모바일 배터리/데이터를 고려해 백그라운드 탭에서 중단(Page Visibility API).
5. 파일 업로드는 한 번에 1개부터 시작하고 파일명·크기·형식을 전송 전에 표시합니다. 대용량·다중 업로드는 진행률·취소·Wi-Fi 권고 UI를 갖춘 뒤 확장합니다.
6. 로컬 스크립트 실행 승인은 도구명, 실행 PC, 입력 요약, 예상 출력 위치를 한 화면에서 확인할 수 있어야 하며 파괴적 실행은 모바일에서도 허용하지 않습니다.
7. Cloud Tool 초안 검토는 제목·본문·일시를 한 화면에서 수정하고, 최소 44px의 복사·취소 버튼을 제공하며 외부 저장 여부를 명시합니다.

## 6. 성공 기준

- 모바일 브라우저에서 1분 안에 업무 1건 등록 → Copilot 브리핑 확인까지 가능하다 (정본 §6과 동일 기준을 모바일에서 충족).
- 데스크톱 전용 연동이 모바일에서 에러가 아니라 명확한 안내로 표시된다.
- ≤480px에서 가로 스크롤 없이 모든 핵심 흐름을 완료할 수 있다.

## 7. 비범위 (Non-Goals)

- 화면마다 네이티브 UI 뷰를 새로 짜는 완전 네이티브 앱 개발 (웹 뷰 방식으로 대체).
- 모바일 전용 별도 프론트엔드 코드베이스 유지 (웹 코어 하나로 통합).
- 모바일 앱 내부에서의 로컬 파일 접근 (데스크톱 전용 기능 유지).

## 8. 현재 모바일 기능의 검증 경계

- 서버 AI 작업은 화면을 떠난 후에도 결과 저장·복귀 조회 경로를 제공한다. [완료 알림 문서](./ai-completion-notifications.md)의 Redis·VAPID·실행 시간 조건을 확인한다.
- 페이지 내 바리스타 독은 모바일 화면을 가리는 영역을 줄이기 위한 UI다. OS 위에 떠 있는 창이 아니다.
- 웹 미니카드는 Document PiP 지원 여부를 감지한다. [Windows 창 제어·전역 단축키](./20-desktop-barista-mini-card.md)는 모바일 기능이 아니다.
- Chrome 온디바이스 AI는 브라우저 런타임 가용성에 의존한다. 모바일에서 언제나 모델이 준비돼 있다고 가정하지 않는다.
- 음성 전사에는 마이크 권한·지원 녹음 형식·Supabase 인증·서버 AI 설정이 필요하다. 선택형/텍스트 입력과 별도로 실기기에서 검증한다.
- 하단 키보드·작은 화면·화면 잠금·복귀·알림 수신은 실제 iOS/Android 기기에서 검증 결과를 남긴다. 이번 문서 갱신은 이를 대신하지 않는다.
