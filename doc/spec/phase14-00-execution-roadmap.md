## 1. 문서 권한과 적용 순서

- `14-data-storage-ai-knowledge-architecture-plan.md`는 제품·데이터 구조의 정본이다.
- 이 문서와 `phase14-01`~`phase14-06`은 실제 구현 범위와 검증 절차의 정본이다.
- 현재 구현 사실이 설계와 다르면 `01-as-built-reference.md`에 실제 상태를 기록하고, 차이는 해당 Phase 체크리스트로 관리한다.
- 한 Phase를 완료하기 전 다음 Phase의 영구 저장 기능을 먼저 배포하지 않는다.
- Supabase 운영 프로젝트의 SQL 실행과 원격 데이터 변경은 사용자가 직접 수행하거나 별도로 승인한 경우에만 진행한다.

## 3. 모든 단계에 적용할 불변 규칙

### 3.1 데이터

- 로그인 사용자의 구조화 데이터 정본은 Supabase Postgres다.
- 로컬 캐시는 서버 데이터를 조용히 덮어쓰지 않는다.
- 원문, 사용자 확정값, AI 초안은 서로 다른 레코드 또는 명확한 상태로 구분한다.
- 모든 신규 데이터에는 `user_id`, 안정적인 ID, 생성·수정 시각, 삭제 정책이 있다.
- 외부 원본은 URL만 저장하지 않고 공급자 ID와 콘텐츠 해시를 함께 관리한다.

### 3.2 개인정보·AI

- `local_only` 자료는 클라우드 AI에 전송하지 않는다.
- 원문 전송이 필요한 AI 요청은 전송 범위와 보관 정책을 확인할 수 있어야 한다.
- AI가 추출한 비용, 일정, 관계는 사용자가 확인하기 전 확정 데이터가 아니다.
- 외부 쓰기는 기존 미리보기 → 1회 승인 → 멱등 실행 흐름을 유지한다.
- 음성 원본은 사용자가 보관을 선택하지 않으면 전사 후 폐기한다.

### 3.3 호환성과 배포

- DB 변경은 `ADD` 중심의 전방 호환 마이그레이션으로 시작한다.
- 기존 컬럼과 API를 즉시 삭제하지 않는다.
- 새 읽기 경로를 검증한 뒤 쓰기 경로를 전환하고 마지막에 레거시를 정리한다.
- 기능 플래그 또는 이중 읽기 기간을 두어 단계별 롤백이 가능해야 한다.
- 운영 데이터에 대한 파괴적 마이그레이션은 별도 문서와 사용자 승인이 필요하다.

## 4. 공통 검증 규약

### 4.1 자동 검증

각 Phase는 최소한 다음 명령을 통과한다.

```powershell
npm run lint
npm run typecheck
npm run test
npm run build
```

현재 테스트 스크립트가 없으므로 Phase 14-01에서 Vitest 기반 `npm run test`를 먼저 추가한다. 브라우저 상호작용은 모바일·PC 핵심 경로에 한해 Playwright 또는 브라우저 수동 검증으로 보완한다.

### 4.2 데이터 검증

- 신규 사용자의 빈 상태
- 기존 localStorage 데이터가 있는 게스트
- 기존 Supabase 데이터가 있는 로그인 사용자
- 같은 계정의 PC·모바일 동시 사용
- 네트워크 단절·복구
- Google 미연동·연동·토큰 만료
- AI 키 없음·할당량 초과·로컬 모델 미실행

### 4.3 보안 검증

- 다른 사용자 ID로 RLS 우회가 불가능한지
- 비공개 첨부에 공개 URL이 만들어지지 않는지
- 로그에 OAuth 토큰, 원문, 음성 데이터가 남지 않는지
- `local_only` 자료가 서버와 Gemini 요청에 포함되지 않는지
- 삭제 요청이 DB·Storage·인덱스에 일관되게 반영되는지

### 4.4 공통 기존 기능 회귀 기준선

각 Phase는 변경 범위와 직접 관련된 항목뿐 아니라 아래 기준선 중 영향 가능성이 있는 항목을 구현 전·후 같은 데이터로 비교한다.

| 영역 | 보존해야 할 기존 동작 |
|---|---|
| 인증 | 게스트 진입, Google 로그인, Google 서비스 연동, 로그아웃 |
| 업무 | 빠른 추가, 완료·보류·삭제, 진행 메모, 하위작업, 오늘의 행동 지침 |
| 메모·문서 | 붙여넣기 추출, 지원 문서 업로드, Drive 옵션, 원문 보기 |
| AI 바리스타 | 기본 브리핑, Q&A, Spark 우선 노출, 미읽음 탭 신호 |
| Cloud Tool | `/tools`, 조회 도구, 초안, Calendar·Drive 승인형 쓰기 |
| 외부 수집 | Outlook, Gmail, Notion, 로컬 문서, Spark 중복 방지 |
| 위젯 | 날씨, 환율·금리, 타이머, YouTube 연속성 |
| 모바일 | 리디렉션 인증, 앱 전환 복귀, 작은 화면 레이아웃 |

구현 전에 기준 항목 수, 주요 응답 예시, 설정 상태를 기록한다. 구현 후 결과가 달라졌다면 의도된 계약 변경인지 문서에 명시하고, 그렇지 않으면 다음 Phase로 진행하지 않는다.

## 5. 단계 게이트

### Gate A — 저장 안전성

- Drive 백업 OFF에서 Drive 쓰기 요청이 0회다.
- 저장 위치와 동기화 상태가 사용자에게 표시된다.
- 현재 누락 필드와 덮어쓰기 위험을 재현하는 테스트가 있다.
- 기존 업무 추가·메모 추출·Google 연동이 회귀하지 않는다.

### Gate B — 데이터 계약·DB

- 신규 마이그레이션을 빈 DB와 기존 스키마 양쪽에 적용할 수 있다.
- 모든 신규 테이블의 RLS와 인덱스를 검증했다.
- 구 버전 클라이언트가 새 스키마에서 기존 기능을 계속 사용한다.
- 타입·DB 매퍼의 왕복 테스트가 통과한다.

### Gate C — 동기화·오프라인

- 로그인 시 로컬과 클라우드 데이터가 소실 없이 병합된다.
- PC와 모바일의 동시 수정 충돌이 탐지된다.
- 오프라인 변경이 중복 없이 재전송된다.
- 전체 목록 교체 삭제 경로가 비활성화됐다.

### Gate D — 원문·관계·AI 결과

- 원문 위치와 파생 항목을 왕복 추적할 수 있다.
- AI 결과에 모델·근거·원본 버전이 기록된다.
- 원본 수정 시 관련 AI 결과가 `stale`로 바뀐다.
- 비공개 첨부와 Drive 연결의 접근 정책이 분리된다.

### Gate E — 비용·음성

- 텍스트·음성 비용 입력이 확인 카드 후 저장된다.
- 모바일에서 마이크 권한 거부·중단·재시도를 처리한다.
- 보관하지 않는 음성 원본이 전사 후 남지 않는다.
- 비용 합계와 원본 영수증 관계가 여러 기기에서 동일하다.

### Gate F — AI 지식 검색

- AI 답변에서 근거 항목과 원문 위치를 확인할 수 있다.
- 사용자·개인정보 정책 필터가 검색보다 먼저 적용된다.
- 오래된 AI 결과를 최신 사실처럼 사용하지 않는다.
- 검색·임베딩 장애 시 관계·키워드 기반 폴백이 동작한다.

## 7. 커밋과 인수인계 단위

- 한 커밋은 한 Phase 내부의 하나의 되돌릴 수 있는 기능 단위를 원칙으로 한다.
- DB 마이그레이션, 서버 계약, 클라이언트 전환을 가능하면 별도 커밋으로 나눈다.
- 각 Phase 완료 시 `01-as-built-reference.md`와 해당 문서 체크리스트를 갱신한다.
- 운영에 사용자가 실행해야 하는 SQL·환경변수·대시보드 설정은 인수인계 항목으로 명시한다.
- 문서에 없는 원격 쓰기, 운영 SQL 실행, 데이터 삭제를 자동으로 수행하지 않는다.
