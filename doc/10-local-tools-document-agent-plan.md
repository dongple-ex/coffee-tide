# 10. 로컬 스크립트·다형식 문서 에이전트 계획

> 상태: **단계 A·B 주요 파서 및 단계 C 읽기 전용 Tool Broker 기반 구현 — 증분 색인·모델 도구 선택·쓰기 도구는 미구현**  
> 기준일: 2026-08-11  
> 상위 계획: [`08-local-ai-enhancement-plan.md`](./08-local-ai-enhancement-plan.md)  
> 외부 AI 연결은 후속 과제: [`09-mcp-access-deferred-plan.md`](./09-mcp-access-deferred-plan.md)

## 1. 목표

CoffeeTide의 로컬 AI를 답변 생성기에 머무르게 하지 않고 다음 작업을 수행하는 **로컬 작업 에이전트**로 확장한다.

1. 사용자가 이미 보유한 PowerShell·Python·Node 스크립트를 등록해 반복 업무에 재사용한다.
2. 여러 폴더와 업로드 파일에서 다양한 문서 형식을 읽고 검색한다.
3. AI가 필요한 도구와 문서를 고르되 임의 명령이나 파일 변경은 직접 수행하지 못하게 한다.
4. 모든 답변과 실행 결과에 사용한 문서·스크립트·실행 상태를 표시한다.

예상 사용 예:

- “지난달 회의록과 Excel 현황표를 읽고 미완료 업무를 정리해줘.”
- “등록한 주간 보고서 스크립트로 초안을 만들되 저장하기 전에 보여줘.”
- “이 폴더의 PDF 계약서에서 갱신일과 담당자만 찾아줘.”
- “오늘 수집 자료를 기존 변환 스크립트로 처리한 뒤 결과를 AI 바리스타 브리핑에 넣어줘.”

## 2. 현재 구현과 한계

### 2.1 문서 처리

| 경로 | 현재 지원 | 주요 제한 |
|---|---|---|
| 브라우저 로컬 폴더 | `.md`, `.txt`, `.docx` | 파일당 512KB, 폴더당 최대 100개 탐색, 최대 10개 업무만 추출, TODO 문형 중심 |
| 서버 `LocalDocAdapter` | `.md`, `.txt`, `.html`, `.htm`, `.xml`, `.docx` | 파일당 2MB, 문서 검색이 아니라 TODO 줄 추출 |
| 파일 업로드 | `.txt`, `.md`, `.csv`, `.json`, `.log`, `.docx` | 2MB 제한, 업로드 전체 텍스트를 단일 항목으로 보관 |
| LLM 산출물 폴더 | `.md`, `.txt` | 앞부분 발췌만 사용, 의미 기반 검색·색인 없음 |

현재 지원하지 않는 대표 형식:

- PDF
- Excel `.xlsx/.xls`
- PowerPoint `.pptx`
- HWP/HWPX
- 이미지 문서와 OCR
- 이메일 원문 `.eml`
- 압축 파일 내부 문서

### 2.2 로컬 스크립트

- 저장소의 `package.json`에는 개발·빌드·검사용 npm 명령만 있다.
- `/api/util/exec-app`은 URL이나 `.exe/.lnk/.app`를 여는 기능이며 스크립트 실행기는 아니다.
- 보안상 `.ps1/.bat/.cmd/.sh` 실행을 의도적으로 막고 있다.
- 스크립트 도구 목록, 인자 스키마, 출력 캡처, 시간 제한, 실행 이력, 사용자 승인 계층이 없다.

따라서 기존 실행기를 넓혀 임의 스크립트를 허용하면 안 된다. 별도의 **등록형 Local Tool Broker**가 필요하다.

## 3. 목표 구조

```text
사용자 요청
  → Local Agent Orchestrator
      ├─ Document Search
      │    ├─ 문서 형식 판별
      │    ├─ 파서/OCR
      │    ├─ 청크·메타데이터·색인
      │    └─ 키워드 + 임베딩 혼합 검색
      └─ Local Tool Broker
           ├─ 등록된 도구 조회
           ├─ 인자 스키마 검증
           ├─ 권한·확인 정책 판정
           ├─ 격리된 프로세스 실행
           └─ 표준 결과·감사 기록
  → 로컬 모델이 근거와 실행 결과를 종합
  → CoffeeTide 확인 UI 또는 브리핑
```

로컬 모델은 실행할 도구와 인자를 **제안**한다. 실제 실행 여부는 Tool Broker가 정책으로 결정한다.

### 3.1 모바일·PC 역할 분리

| 사용 환경 | 문서 입력 | 문서 검색 | 로컬 스크립트 |
|---|---|---|---|
| 모바일 + Vercel | OS 파일 선택기로 개별 업로드 | 업로드·클라우드 보관 문서 | 사용 불가 |
| 모바일 + 같은 네트워크의 PC CoffeeTide | 개별 업로드 | PC가 색인한 결과 조회 가능 | PC에서 실행, 모바일은 미리보기·승인·결과 확인 |
| PC + Vercel | 개별 업로드 | 업로드·클라우드 보관 문서 | 사용 불가 |
| PC 로컬 CoffeeTide | 개별 업로드 + 폴더 연결 | 전체 로컬 색인 | 등록된 도구 실행 가능 |

모바일 브라우저에서 `showDirectoryPicker`가 없다는 이유로 문서 기능 전체를 숨기지 않는다. 폴더 연결 버튼만 데스크톱 전용으로 처리하고, 표준 `<input type="file">` 기반 개별 업로드는 항상 제공한다. 향후 하이브리드 앱에서는 네이티브 문서 선택기 결과를 동일한 업로드 API에 연결한다.

## 4. 다형식 문서 수집 설계

### 4.1 공통 파서 계약

문서별 파싱 로직을 업로드 API와 폴더 스캐너에 중복 구현하지 않고 공통 계층으로 분리한다.

```ts
interface DocumentParser {
  supports(file: DocumentFileInfo): boolean;
  extract(file: DocumentInput): Promise<ExtractedDocument>;
}

interface ExtractedBlock {
  text: string;
  page?: number;
  sheet?: string;
  slide?: number;
  heading?: string;
  cellRange?: string;
}

interface ExtractedDocument {
  title: string;
  blocks: ExtractedBlock[];
  metadata: Record<string, string | number>;
  warnings: string[];
}
```

페이지·시트·슬라이드·셀 범위를 보존해야 답변에서 정확한 근거를 표시할 수 있다.

### 4.2 형식별 단계

| 단계 | 형식 | 처리 원칙 |
|---|---|---|
| 1차 | TXT, Markdown, JSON, CSV, LOG, HTML/XML, DOCX | 현재 기능을 공통 파서로 통합하고 인코딩·표·제목 구조를 보존 |
| 2차 | PDF, XLSX, PPTX | PDF 페이지, Excel 시트/범위, PowerPoint 슬라이드 단위로 추출 |
| 3차 | HWPX, EML | 구조화된 XML·메일 헤더/본문/첨부 메타데이터 추출 |
| 선택 | 스캔 PDF, PNG/JPEG | 로컬 OCR 엔진이 설정된 경우에만 실행하고 OCR 여부 표시 |
| 보류 | 구형 HWP, 암호화 문서, 압축 파일 | 별도 변환 도구·비밀번호·압축 해제 정책 확정 후 지원 |

문서에 매크로나 포함 스크립트가 있어도 실행하지 않는다. 파서는 읽기 전용으로 텍스트와 메타데이터만 추출한다.

### 4.3 색인과 검색

1. 파일 경로, 크기, 수정 시각, SHA-256 해시를 기록한다.
2. 해시가 변경된 문서만 다시 파싱한다.
3. 제목·문단·페이지·시트 경계를 우선해 청크를 만든다.
4. 키워드 검색과 임베딩 검색을 함께 사용한다.
5. 상위 결과를 재정렬하고 필요한 조각만 모델에 전달한다.
6. 답변에 파일명과 페이지/시트/슬라이드를 표시한다.

초기에는 로컬 SQLite 또는 파일 기반 메타데이터 저장소를 사용하고, 실제 문서 규모와 검색 시간을 측정한 뒤 별도 벡터 DB 도입 여부를 결정한다.

### 4.4 폴더와 권한

- 사용자가 직접 선택한 폴더만 읽는다.
- 기본 제외 폴더는 `.git`, `.next`, `node_modules`, 숨김 폴더, 휴지통으로 유지한다.
- 폴더별로 `검색 허용`, `AI 원문 허용`, `클라우드 폴백 허용`을 분리한다.
- 삭제·이동·덮어쓰기는 문서 검색 기능에 포함하지 않는다.
- Vercel에서는 PC 폴더를 읽을 수 없으므로 로컬 CoffeeTide 또는 향후 로컬 브리지에서만 동작한다.
- 모바일의 개별 업로드는 폴더 권한을 요구하지 않으며, 선택한 파일 한 건만 서버로 전송한다.
- 모바일 데이터 사용량을 고려해 1차는 단일 파일·2MB 제한을 유지하고, 형식별 파서와 스트리밍 저장 정책을 검증한 뒤 상향한다.

## 5. 로컬 스크립트 도구 설계

### 5.1 등록 방식

임의 폴더의 스크립트를 자동 발견해 실행하지 않는다. 사용자가 스크립트와 실행 정책을 명시적으로 등록한다.

예시 도구 정의:

```json
{
  "id": "weekly-report",
  "name": "주간 보고서 초안 생성",
  "runtime": "powershell",
  "scriptPath": "C:\\WorkTools\\weekly-report.ps1",
  "workingDirectory": "C:\\WorkTools",
  "inputSchema": {
    "type": "object",
    "properties": {
      "from": { "type": "string", "format": "date" },
      "to": { "type": "string", "format": "date" }
    },
    "required": ["from", "to"]
  },
  "timeoutMs": 60000,
  "maxOutputBytes": 1048576,
  "effect": "prepare_file",
  "confirmation": "always"
}
```

실제 설정에는 비밀번호와 API 키를 넣지 않는다. 필요한 비밀 값은 서버 전용 환경 변수 이름만 허용 목록으로 연결한다.

### 5.2 지원 런타임

| 런타임 | 실행 방법 | 비고 |
|---|---|---|
| PowerShell | 고정된 `powershell.exe`/`pwsh` + `-File` + 검증된 인자 | 명령 문자열 조합 금지 |
| Python | 설정에서 검증한 Python 실행 파일 + 스크립트 경로 + 인자 | 가상환경 경로를 도구별 지정 가능 |
| Node.js | 고정된 Node 실행 파일 + `.js/.mjs` + 인자 | 패키지 설치를 실행 중 자동 수행하지 않음 |
| 실행 파일 | 허용된 절대 경로 + 인자 | 기존 앱 열기와 업무 도구 실행을 구분 |

`.bat/.cmd`는 셸 재파싱 위험이 크므로 1차 지원에서 제외한다. 필요하면 검증된 래퍼 스크립트로 전환한 뒤 별도 승인한다.

### 5.3 실행 정책

- `spawn`/`execFile`과 `shell:false`를 사용한다.
- 실행 파일, 스크립트, 작업 폴더는 등록 당시의 절대 경로와 파일 해시로 고정한다.
- AI가 실행 경로, 런타임, 환경 변수 이름을 변경할 수 없게 한다.
- 입력은 JSON Schema로 검증하고 문자열 길이, 날짜, 열거형, 허용 경로를 제한한다.
- 시간 제한과 최대 표준 출력·표준 오류 크기를 강제한다.
- 프로세스 ID, 시작/종료 시각, 종료 코드, 도구 버전, 승인자를 기록한다.
- 결과는 `{ success, summary, artifacts, warnings, exitCode }` 형태로 정규화한다.
- 결과 파일은 도구별 허용 출력 폴더에만 생성할 수 있게 한다.

운영체제 수준의 완전한 샌드박스가 없는 상태에서는 신뢰하지 않는 스크립트를 등록하지 않는다.

### 5.4 읽기와 쓰기 등급

| 등급 | 예 | 실행 조건 |
|---|---|---|
| `read_only` | 문서 변환, 상태 조회, 검색, 통계 | 최초 승인 후 자동 실행 선택 가능 |
| `prepare_file` | 보고서 초안, 변환본 생성 | 실행 전 또는 결과 저장 전 확인 |
| `write_local` | 기존 파일 수정, 이름 변경 | 매번 대상과 변경 내용을 표시하고 확인 |
| `external_write` | Google Calendar, Drive, 메일, 원격 API | 항상 기존 CoffeeTide 확인 UI를 거침 |
| `destructive` | 삭제, 대량 이동, 계정·권한 변경 | 초기 범위에서 금지 |

## 6. AI 도구 선택과 실행 흐름

```text
1. 사용자 요청 분석
2. 관련 문서 검색
3. 필요한 등록 도구 후보와 인자 제안
4. Tool Broker의 스키마·권한 검사
5. 확인이 필요하면 실행 미리보기 표시
6. 사용자 승인
7. 로컬 실행 및 결과 캡처
8. 로컬 모델이 결과 요약
9. 사용 문서·도구·출력 파일 표시
```

AI가 확신하지 못하면 임의로 도구를 고르지 않고 사용자에게 대상 기간·파일·출력 위치를 묻는다.

## 7. UI 제안

설정의 `로컬 AI` 아래에 다음 영역을 둔다.

- 연결된 로컬 모델과 상태
- 검색 폴더 목록과 형식별 파서 상태
- 등록된 로컬 도구 목록
- 도구별 읽기/쓰기 등급과 확인 정책
- 최근 실행 이력과 실패 사유
- 색인 문서 수, 마지막 색인 시각, 재색인 버튼

모바일에서는 폴더 연결·재색인·런타임 경로 편집을 숨기고 다음 동작을 우선한다.

- `문서 첨부`를 OS 파일 선택기로 연결
- 업로드 전 파일명·형식·크기 표시
- 업로드/파싱 진행 상태와 취소
- 문서 검색 결과의 파일명·페이지/시트 출처 열기
- 로컬 도구 실행 미리보기·승인·결과 확인

AI 바리스타 답변에는 다음 배지를 필요한 경우에만 표시한다.

- `로컬 문서 3개 참조`
- `로컬 도구: 주간 보고서`
- `실행 전 확인 필요`
- `로컬 실행 실패 — 규칙 엔진으로 전환`

- [ ] 실제 대용량·복합 문서 샘플로 정확도와 메모리 사용량 검증

### 단계 C — 읽기 전용 Tool Broker

- [x] 도구 정의 스키마와 설정 내 등록 상태·실행 화면 (`LOCAL_TOOL_REGISTRY_PATH` 기반 로컬 JSON)
- [x] PowerShell·Python·Node 고정 런타임 실행기
- [x] 인자 검증, 스크립트 SHA-256, 타임아웃, 출력 상한, 비밀 환경변수 차단, 감사 기록
- [x] 실행 PC·입력 미리보기와 5분 유효 1회 승인 토큰
- [x] Vercel 차단, 모바일에서 같은 PC 실행 승인 흐름
- [ ] 운영체제 수준 샌드박스와 실제 보유 읽기 전용 스크립트 2~3개 등록

### 단계 D — 로컬 모델 도구 선택

- 로컬 모델의 구조화된 tool call을 Tool Broker 제안으로 변환
- 등록되지 않은 도구·인자 거부
- 문서 검색과 도구 실행 결과를 한 답변에서 결합

### 단계 E — 확인형 쓰기 작업

- `prepare_file`부터 시작
- 실행 전 대상·예상 결과·출력 위치 미리보기
- 기존 업무·일정 확인 UI 재사용
- 외부 쓰기와 파괴적 작업은 별도 승인 전까지 제외

### 단계 F — HWPX·EML·OCR

- 실제 보유 문서 수요를 확인한 뒤 순차 추가
- OCR은 로컬 엔진 상태와 처리 시간을 UI에 표시
- 변환 실패 문서는 지원 불가 사유를 명시

## 9. 테스트 계획

### 문서

- 형식별 정상, 빈 문서, 손상 문서, 암호화 문서
- 한글·영문 혼합, 표, 다중 시트, 다중 페이지
- 같은 파일 재스캔 시 중복 색인 방지
- 변경 파일만 재파싱
- 페이지·시트·슬라이드 출처 일치
- 대용량 파일 제한과 메모리 상한
- 문서 안의 프롬프트 인젝션 문구 무시

### 도구

- 정상 종료, 비정상 종료, 시간 초과, 과도한 출력
- 스키마에 없는 인자와 허용 경로 밖 접근 거부
- 등록 후 스크립트 파일이 변경된 경우 실행 중단
- 쓰기 등급별 확인 UI 강제
- Vercel에서 로컬 도구 실행 403
- 원문·비밀 값이 실행 로그에 남지 않는지 확인

## 10. 완료 기준

- PDF·DOCX·XLSX·PPTX를 같은 검색 인터페이스에서 조회할 수 있다.
- 답변이 파일명과 페이지·시트·슬라이드 근거를 표시한다.
- 변경되지 않은 문서는 다시 파싱·임베딩하지 않는다.
- 등록된 PowerShell·Python·Node 도구를 검증된 인자로 실행할 수 있다.
- AI는 등록되지 않은 명령이나 경로를 실행할 수 없다.
- 쓰기 작업은 등급에 따라 반드시 사용자 확인을 거친다.
- 실행 도구, 입력 요약, 종료 상태, 결과 파일을 사용자가 확인할 수 있다.
- 로컬 모델이나 스크립트가 실패해도 CoffeeTide 기본 업무 기능은 계속 동작한다.

## 11. 이번 작업 범위

2026-08-11에는 현재 소스의 문서·실행 제한과 모바일 동작을 점검하고 단계 A·B의 주요 파서와 단계 C 읽기 전용 Tool Broker 기반을 구현했다. 공통 파서가 텍스트·Markdown·CSV·JSON·LOG·HTML/XML·DOCX·PDF·XLSX·PPTX를 처리하며 업로드·브라우저 폴더·서버 로컬 문서 어댑터가 이를 공유한다. PDF는 페이지, Excel은 시트·셀 범위, PowerPoint는 슬라이드 번호를 표시한다. Tool Broker는 별도 API와 설정 UI에서 신뢰한 스크립트만 고정 해시·검증된 인자로 실행하고, 모바일에서도 같은 PC에 접속한 경우 미리보기·승인을 거친다. 실제 로컬 모델의 도구 선택, 쓰기 도구, 증분 색인, HWPX·EML·OCR은 아직 변경하지 않는다.

### 11.1 로컬 도구 등록 절차

1. 읽기 전용 스크립트의 해시를 계산한다: `Get-FileHash -Algorithm SHA256 C:\\WorkTools\\tool.ps1`
2. [`local-tools.registry.example.json`](./local-tools.registry.example.json)을 복사해 실제 절대 경로, 실행 파일 경로(Python/Node), 인자와 소문자 SHA-256을 입력한다.
3. `.env.local`의 `LOCAL_TOOL_REGISTRY_PATH`에 등록 JSON의 절대 경로를 지정하고 CoffeeTide를 재시작한다.
4. 설정 → `로컬 AI 도구`에서 입력값을 채우고 미리보기의 실행 PC·스크립트·인자를 확인한 뒤 승인한다.

등록 JSON과 실제 스크립트는 Git에 넣지 않는 경로에 두는 것을 권장한다. 현재 구현은 `read_only`와 `confirmation: always`만 허용하며, `.bat/.cmd/.sh`와 임의 명령 문자열은 지원하지 않는다.
