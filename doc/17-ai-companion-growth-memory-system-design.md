> 상태: **핵심 제품 결정 확정 · 구현 전**  
> 기준일: 2026-09-01  
> 적용 대상: CoffeeTide AI 바리스타, Copilot 대화, 업무·집중·회고 흐름  
> 관련 문서: [`00-product-spec.md`](./00-product-spec.md), [`14-data-storage-ai-knowledge-architecture-plan.md`](./14-data-storage-ai-knowledge-architecture-plan.md), [`16-ai-character-productivity-companion-architecture.md`](./16-ai-character-productivity-companion-architecture.md), [`spec/phase14-06-ai-knowledge-retrieval.md`](./spec/phase14-06-ai-knowledge-retrieval.md)

> 후속 정본: 사용자의 발화를 자연 대화·소통 회복·업무·혼합·실행 요청으로 구분하는 규칙은 [`18-ai-companion-natural-conversation-orchestration-design.md`](./18-ai-companion-natural-conversation-orchestration-design.md)를 따른다. 자연 대화 라우팅과 충돌하는 경우 해당 문서를 우선 적용한다.

## 1. 문서 목적

이 문서는 인터랙티브 캐릭터 서비스의 **다층 기억, 관계 상태 전이, 맥락적 회상, 분기 트리거** 구조를 CoffeeTide에 맞게 다시 설계한다. 목표는 단순히 캐릭터 호감도 숫자를 올리거나 대사를 화려하게 만드는 것이 아니다.

CoffeeTide에 도입할 핵심은 다음 세 가지다.

1. AI 바리스타가 사용자의 선택과 작업 맥락을 기억해 대화가 누적되는 느낌을 만든다.
2. 재미 요소가 실제 업무 실행, 자기 이해, 회고 습관을 돕도록 연결한다.
3. 사용자를 붙잡기 위한 압박이 아니라, 사용자가 점점 AI 없이도 더 잘 계획하고 실행하도록 돕는다.

첨부된 분석 문서는 아이디어 출처이며 CoffeeTide의 구현 사실이나 외부 서비스의 공식 명세로 간주하지 않는다. 특히 자극적인 집착·통제형 분기, 사용자의 자율성을 제한하는 연출, 설명되지 않는 내부 추론 노출은 CoffeeTide에 적용하지 않는다.

## 2. 핵심 결정 요약

### 2.1 제품 모델

CoffeeTide는 하나의 호감도 수치로 모든 것을 표현하지 않고 다음 두 축을 분리한다.

| 축 | 의미 | 범위 | 사용자에게 보이는 방식 |
|---|---|---|---|
| **동반자 관계(Bond)** | 선택한 캐릭터와 함께한 경험과 신뢰 | 캐릭터별 | 관계 단계, 대사 변화, 기념 장면 |
| **사용자 성장(Growth)** | 실행·집중·정리·회고 습관의 변화 | 계정 공통 | 주간 성장 카드, 패턴, 다음 실험 |

관계 레벨은 재미와 연속성을 담당한다. 사용자 성장은 실제 행동 근거를 바탕으로 사용자가 무엇을 더 잘하게 되었는지 설명한다. 관계 레벨이 높다고 사용자가 더 생산적인 사람이라는 뜻은 아니다.

### 2.2 기본 정책

1. **핵심 생산성 기능은 관계 레벨로 잠그지 않는다.** 레벨 보상은 캐릭터 연출, 선택형 템플릿, 기념 배지, 추천 방식의 다양화가 중심이다.
2. **관계 단계는 강등하지 않는다.** 오래 쉬거나 업무를 못 끝냈다는 이유로 친밀도를 깎지 않는다.
3. **현재 컨디션은 별도 상태로 다룬다.** `몰입`, `정체`, `과부하`, `회복`은 일시적이며 관계 단계와 섞지 않는다.
4. **완료 건수만으로 성장시키지 않는다.** 계획, 중요한 일의 진전, 회고, 휴식 선택, 사용자가 승인한 학습을 함께 본다.
5. **LLM은 상태 전이를 결정하지 않는다.** 규칙 엔진이 검증된 이벤트로 상태를 바꾸고, LLM은 그 상태를 자연스럽게 표현한다.
6. **기억은 사용자가 확인·수정·삭제할 수 있다.** 민감한 내용은 자동 장기 기억으로 승격하지 않는다.
7. **Mock·샘플·실데이터를 구분한다.** 샘플 업무로 획득한 성장이나 관계 경험치는 실제 계정 성장으로 합산하지 않는다.
8. **시험 운영 중 기능 전체를 안전하게 켜고 끌 수 있어야 한다.** 비활성화해도 기본 AI 바리스타와 핵심 업무 기능은 계속 동작한다.

## 3. 현재 기준선과 설계 격차

이 기준선은 2026-09-01 로컬 작업 트리를 기준으로 한다. 커밋·원격 반영, 브라우저 확인, 로그인 상태의 Supabase E2E 검증을 의미하지 않는다.

### 3.1 재사용할 기반

| 영역 | 현재 위치 | 현재 상태 | 재사용 방향 |
|---|---|---|---|
| 캐릭터 프리셋·어조 | `src/lib/ai/harness.ts` | 12종 프리셋과 행동 지문 규칙이 작업 중 | 관계 단계별 어조 오버레이 추가 |
| 관계 EXP | `src/lib/ai/affectionManager.ts` | 캐릭터별 `localStorage`, 5단계, 업무 완료 이벤트 | 이벤트 원장 기반 계산기로 교체 |
| 관계 UI | `AffectionBadge.tsx` | 게이지·칭호·보상 설명 | 근거, 성장과의 구분, 기억 관리 진입점 추가 |
| 빠른 응답 | `copilotQuickReplies.ts` | 업무 상태·시간대·페르소나 기반 칩 | 현재 모드·성장 실험 기반 선택지 추가 |
| 대화 요청 | `POST /api/copilot` | 현재 질문과 업무 컨텍스트 전달 | 세션·에피소드·장기 기억 패키지 추가 |
| 지식 검색 | `src/lib/knowledge/*` | 업무·문서 관계/키워드 기반 근거 검색 | 개인 기억 검색과 분리하되 동일 근거 형식 사용 |
| 데이터 기반 | Supabase `unified_items`, `item_relations`, `ai_artifacts` | 구조화 데이터·관계·AI 파생 결과·RLS 기반 | 성장 이벤트와 기억 전용 테이블 추가 |
| 게스트 저장 | 브라우저 저장소 | 업무·화면 상태·대화 스냅샷 일부 저장 | IndexedDB 기반 로컬 기억 저장소 추가 |

### 3.2 현재 부족한 점

- 대화 UI에는 과거 메시지가 남지만 `/api/copilot` 요청은 현재 질문 한 건만 전달하므로 실제 대화 연속성이 없다.
- 관계 상태가 브라우저의 `localStorage`에만 있어 기기 간 이어지지 않는다.
- 현재 실제 EXP 연결은 업무 완료가 중심이며, 선언된 다른 액션과 보상 기능은 실제 실행 권한과 연결되지 않았다.
- 완료를 취소했다 다시 완료하거나 작은 업무를 다수 만드는 행위를 방지할 이벤트 멱등성·일일 상한이 없다.
- 관계 변화와 사용자 성장 지표가 하나의 EXP로 섞여 있다.
- 에피소드 요약, 확인된 사용자 선호, 중요한 약속, 회상 이력이 없다.
- 사용자가 AI가 무엇을 기억하는지 보고 지우는 화면이 없다.
- 과부하·정체·회복을 감지해 개입 강도를 낮추는 규칙이 없다.
- 레벨별 보상 문구는 표시되지만 실제 기능 해금 여부를 판정하는 도메인 계층이 없다.

## 4. 목표와 제외 범위

### 4.1 목표

- 첫날에도 유용하고, 2주 뒤에는 사용자의 업무 방식에 맞게 달라진다.
- 과거의 선택을 자연스럽게 회상하되 사용자를 감시하는 느낌을 주지 않는다.
- 캐릭터의 말투가 변해도 업무 사실, 날짜, 출처, 실행 승인 규칙은 변하지 않는다.
- 완료만 칭찬하지 않고 계획 조정, 도움 요청, 휴식, 회고도 좋은 선택으로 인정한다.
- 사용자는 자신의 성장 근거와 AI 기억을 언제든 검토할 수 있다.
- 게스트도 로컬 전용으로 시작할 수 있고 로그인 시 명시적 동의 후 병합할 수 있다.

### 4.2 제외 범위

- 실제 인간관계나 정신 상태를 진단하는 기능
- 생산성 점수를 인사평가·성과평가에 사용하는 기능
- 결제 재화, 랜덤박스, 경쟁 순위표
- 연속 접속 실패 시 손실을 주는 스트릭
- 캐릭터가 사용자를 질투·협박·비난해 행동을 강제하는 분기
- 모델의 숨은 사고 과정(Chain of Thought)을 저장하거나 사용자에게 노출하는 기능
- 사용자 승인 없는 외부 메일 발송, 일정 생성, 문서 저장

## 5. 경험 구조: 관계와 성장의 이중 루프

```text
사용자 행동
   │
   ├─ 실제 작업 이벤트 ──→ 성장 원장 ──→ 주간 패턴·다음 실험
   │                          │
   └─ 의미 있는 상호작용 ─→ 관계 원장 ──→ 관계 단계·기념 장면
                              │
                              ▼
                    기억 검색 + 현재 모드 판단
                              │
                              ▼
                 캐릭터답지만 근거 있는 응답·선택지
                              │
                              ▼
                     사용자 승인·수정·피드백
```

### 5.1 사용자 성장 4축

성장은 하나의 총점 대신 최근 14일과 이전 14일을 비교한 네 가지 흐름으로 보여준다.

| 성장 축 | 관찰 근거 | 좋은 변화의 예 | 금지할 해석 |
|---|---|---|---|
| **실행** | 계획한 중요 업무의 진전·완료·재계획 | 중요한 일의 완료율 상승 | 완료 건수가 많으면 무조건 우수 |
| **집중** | 타이머 세션, 방해 후 복귀, 적정 휴식 | 긴급하지 않은 일에도 집중 블록 확보 | 오래 일할수록 우수 |
| **정리** | 캡처한 메모를 업무·문서로 구조화, 후속 작업 연결 | 미분류 항목 감소 | 기록량이 많으면 우수 |
| **회고** | 일일·주간 회고, 추정과 실제 차이 확인 | 자신에게 맞는 작업 시간대 발견 | 매일 접속해야 우수 |

성장 카드는 평가 문구보다 관찰과 제안을 사용한다.

> 최근 2주에는 오전에 정한 1순위 업무를 끝낸 날이 4일에서 7일로 늘었어요. 다음 주에는 회의가 많은 화요일만 1순위를 더 작게 잡아볼까요?

### 5.2 관계 5단계

기존 Phase 16의 5단계 명칭과 임계값은 초기 호환성을 위해 유지한다. 다만 `EXP`는 단순 클릭 수가 아니라 검증된 관계 이벤트에서만 계산한다.

| 단계 | 관계 표현 변화 | 보상 원칙 | 영구 상태 |
|---|---|---|---|
| Lv.1 `낯선 시작` | 정중하고 설명이 충분함 | 기본 대사·브리핑 | 시작 시점 |
| Lv.2 `믿음직한 동료` | 사용자가 선호한 업무 방식 반영 | 선호 템플릿·호칭 선택 | 첫 합의된 작업 방식 |
| Lv.3 `척하면 척 단짝` | 확인된 기억을 가볍게 회상 | 캐릭터별 기념 장면·대사 세트 | 첫 유효 회상 피드백 |
| Lv.4 `각별한 파트너` | 제안 길이·강도를 개인화 | 주간 회고 연출·선택형 자동화 추천 | 반복 패턴을 사용자가 승인 |
| Lv.5 `소울메이트` | 사용자가 정한 협업 규칙을 안정적으로 유지 | 장기 여정 카드·시즌 회고 | 충분한 기간과 복수의 성장 축 |

핵심 브리핑, 캔버스, 회고, 데이터 검색 기능 자체는 모든 단계에서 사용할 수 있다. 높은 단계는 **표현과 편의의 개인화**를 해금하지, 사용자의 데이터를 인질로 삼지 않는다.

### 5.3 일시적 현재 모드

관계 단계와 별도로 최근 신호에서 현재 모드를 정한다.

| 모드 | 진입 신호 | AI 행동 | 종료 조건 |
|---|---|---|---|
| `momentum` | 중요한 작업 진전, 다음 행동이 명확 | 짧은 축하 + 다음 1개 제안 | 정체·과부하 신호 또는 세션 종료 |
| `focus` | 집중 타이머 시작, 방해 최소화 선택 | 불필요한 개입 억제 | 타이머 종료·사용자 중단 |
| `stuck` | 같은 작업 반복 연기, 도움 요청 | 일을 5~15분 단위로 축소 | 첫 하위 단계 완료·재계획 |
| `overloaded` | 긴급 항목 과다, 반복 취소, 늦은 시간 과업 증가 | 우선순위 축소·휴식/연기 제안 | 사용자가 계획을 줄이거나 휴식 선택 |
| `reflection` | 하루 마감·주간 회고 시작 | 사실 기반 회고 질문 1~3개 | 회고 저장·건너뛰기 |
| `returning` | 일정 기간 후 재방문 | 죄책감 없는 재시작 안내 | 첫 계획 또는 작업 실행 |

## 6. 핵심 사용자 여정

### 6.1 첫 3분

1. 캐릭터를 선택한다.
2. 기억·성장 기능을 한 문장으로 안내한다.
3. 업무를 직접 추가하거나 기존 소스를 연결한다.
4. AI 바리스타가 “오늘 가장 가볍게 시작할 한 가지”를 제안한다.
5. 사용자가 제안을 채택·수정·거절하면 그 선택을 첫 작업 방식 신호로 기록한다.

연동이 없거나 샘플 데이터만 있으면 “현재는 직접 입력한 내용/샘플을 기준으로 안내 중”이라고 표시한다. 샘플 이벤트는 영구 성장에 합산하지 않는다.

### 6.2 아침 브리핑

1. 오늘의 업무와 일정 근거를 조회한다.
2. 최근 회고에서 확인된 선호 한두 개만 적용한다.
3. `오늘의 1순위`, `예상 방해 요소`, `시작 버튼`을 제시한다.
4. 캐릭터 연출은 1~2문장으로 제한하고 실제 다음 행동을 앞에 둔다.

### 6.3 작업 중 정체

1. 같은 업무의 연기·재오픈 또는 사용자의 도움 요청을 감지한다.
2. 관계 단계는 유지하고 현재 모드만 `stuck`으로 바꾼다.
3. 과거에 효과가 있었다고 사용자가 확인한 방식이 있으면 한 번만 회상한다.
4. `5분만 시작`, `하위 작업 3개`, `오늘 범위 줄이기` 중 선택지를 준다.

### 6.4 완료 순간

1. 동일 항목의 최초 유효 완료인지 멱등성 키로 확인한다.
2. 중요도·계획 여부·사용자 수정 여부를 반영해 이벤트를 기록한다.
3. 축하는 짧게 하고 다음 행동을 강요하지 않는다.
4. 연속 작업을 제안하기 전에 `잠깐 쉬기`를 동등한 선택지로 둔다.

### 6.5 하루 마감

1. 완료·진전·재계획 사실을 보여준다.
2. “잘한 점”, “걸린 점”, “내일 바꿀 한 가지”를 묻는다.
3. 사용자가 선택한 내용만 에피소드 기억 후보가 된다.
4. 회고를 건너뛰어도 관계 점수나 연속 기록을 잃지 않는다.

### 6.6 주간 성장 카드

1. 최근 14일과 이전 14일을 비교한다.
2. 최소 표본 기준을 넘은 패턴만 설명한다.
3. 인과관계가 아니라 관찰임을 명시한다.
4. 다음 주 실험은 하나만 추천하고 사용자가 채택해야 활성화한다.

### 7.2 기억의 생명주기

```text
관찰
  → 기억 후보 생성
  → 민감도·근거·중복 검사
  → 자동 임시 저장 또는 사용자 확인
  → 활성 기억
  → 관련 상황에서 제한적 회상
  → 사용자의 도움됨/틀림 피드백
  → 강화·수정·만료·삭제
```

### 7.3 기억 후보 분류

| 후보 | 예 | 기본 처리 |
|---|---|---|
| 표현 선호 | “답은 세 줄로 먼저 보여줘” | 자동 임시 저장, 반복되면 확인 요청 |
| 작업 방식 | “오전에는 기획, 오후에는 회의가 편함” | 패턴 근거와 함께 사용자 확인 |
| 호칭·캐릭터 설정 | “팀장님이라고 불러줘” | 즉시 저장, 설정 화면에서 수정 가능 |
| 중요한 약속 | “금요일마다 주간 회고” | 사용자 확인 후 저장 |
| 민감 정보 | 건강, 가족, 재정 곤란, 갈등 | 자동 장기 저장 금지 |
| 추론된 성격 | “완벽주의자 같다” | 장기 기억 금지, 사실처럼 표현 금지 |
| 외부 문서의 사실 | 프로젝트 문서 내용 | 개인 기억이 아니라 기존 지식 근거로 조회 |

### 7.4 회상 점수

관련 기억은 다음 점수로 정렬하되, 민감도와 사용자 설정이 우선한다.

```text
recallScore =
  0.35 × semanticRelevance
+ 0.20 × recency
+ 0.20 × userConfirmed
+ 0.15 × priorHelpfulness
+ 0.10 × currentModeFit
- sensitivityPenalty
- repetitionPenalty
```

- 같은 기억은 7일 내 세 번 이상 능동 회상하지 않는다.
- `userConfirmed=false`인 기억은 단정형 문장에 사용하지 않는다.
- 근거가 충돌하면 가장 최근 사용자 확인을 우선하고 확인 질문을 한다.
- 회상할 내용이 없으면 억지로 과거를 언급하지 않는다.

### 7.5 자연스러운 회상 표현

나쁜 예:

> 지난 8월 21일에 당신은 오전 집중을 선호한다고 말했습니다.

좋은 예:

> 오전엔 긴 설명보다 바로 시작하는 쪽이 잘 맞았죠. 25분만 먼저 열어둘까요?

UI에는 `왜 이렇게 제안했나요?`를 제공해 다음 근거를 펼칠 수 있게 한다.

- 사용자가 확인한 선호
- 관련된 과거 회고
- 현재 업무·일정
- 사용된 기억을 끄거나 수정하는 버튼

## 8. 이벤트·상태 전이·분기 엔진

### 8.1 처리 파이프라인

```text
도메인 이벤트 수신
  → 출처·사용자·샘플 여부 검증
  → idempotency_key 중복 제거
  → 이벤트 정규화
  → 관계/성장 규칙 각각 평가
  → 상태 전이 원장 기록
  → 기억 후보 생성
  → 응답 컨텍스트 패키지 생성
  → UI 이벤트 발행
```

### 8.2 이벤트 신뢰 경계

#### 8.2.1 권위 수준

이벤트는 발생 위치가 아니라 **검증 가능한 근거**에 따라 권위를 구분한다.

| 권위 | 생성 주체 | 예 | 관계 반영 | 성장 반영 |
|---|---|---|---|---|
| `server_domain` | 실제 업무 변경을 처리한 서버 도메인/RPC | 업무 최초 완료, AI 산출물 채택, 회고 저장 | 가능 | 가능 |
| `server_receipt` | 서버가 시작·완료를 모두 확인한 상호작용 | 서버 발급 집중 세션, 브리핑 제안 채택 | 가능 | 가능 |
| `local_provisional` | 게스트 또는 오프라인 클라이언트 | 로컬 업무 완료, 로컬 타이머 | 로컬에서만 임시 반영 | 클라우드 성장 반영 금지 |
| `legacy_import` | 로그인 시 사용자가 승인한 기존 로컬 관계 스냅샷 | Phase 16 `localStorage` 관계 상태 | 관계 연속성만 반영 | 성장 반영 금지 |
| `diagnostic` | 동의한 `shadow` 코호트의 규칙 평가 | 이벤트 유형·판정 결과 | 불가 | 불가 |

로그인 사용자의 클라우드 관계·성장 정본에는 `server_domain`, `server_receipt`만 점수 이벤트로 반영한다. 브라우저가 주장한 완료, 중요도, 지속 시간만으로는 점수를 만들지 않는다.

#### 8.2.2 서버 생성 원칙

- 브라우저가 `bond_delta`, 관계 단계, 성장 축, 중요도 가중치, `credited_day`를 전송할 수 없게 한다.
- 로그인 사용자의 `task_completed`는 `unified_items.status`를 실제로 변경한 서버 작업에서만 생성한다.
- 업무 상태 변경과 신뢰 가능한 mutation/outbox receipt 기록은 하나의 DB 트랜잭션/RPC에서 처리한다.
- `companion_events` 삽입, 일일 상한 적용, `companion_profiles` 갱신은 receipt를 소비하는 별도 멱등 트랜잭션에서 처리한다.
- 클라이언트가 같은 요청을 반복해도 UNIQUE 멱등 키 충돌은 성공적인 무처리로 응답하고 업무 변경 자체를 실패시키지 않는다.
- 직접 DB 쓰기 권한은 제한한다. `authenticated` 클라이언트가 `companion_events`의 `INSERT`, `UPDATE`, `DELETE`를 직접 수행하지 못하게 하고, 사용자·원본 상태를 재검증하는 서버 경로만 사용한다.
- 이벤트 소비가 실패해도 이미 성공한 업무 완료를 롤백하지 않는다. 기존 `sync_mutation_receipts` 또는 전용 outbox에 남은 receipt를 재시도한다.

권장 서버 처리:

```text
업무 상태 변경 요청
  → auth.uid()와 항목 소유권 검증
  → 현재 상태가 completed가 아닌지 확인
  → 업무 상태·버전 갱신 + mutation/outbox receipt 기록(동일 트랜잭션)
  → 업무 변경 결과 반환
  → receipt 소비 시작
  → 서버가 event_type/source/policy_version/idempotency_key 생성
  → 일일 상한 계산
  → companion_events INSERT ON CONFLICT DO NOTHING
  → 실제 삽입된 경우에만 companion_profiles 캐시 갱신
  → UI에 관계 변화 이벤트 전달 또는 다음 profile 조회에서 반영
```

#### 8.2.3 이벤트별 멱등 키

멱등 키는 `(user_id, idempotency_key)` UNIQUE로 강제한다. 반복 완료를 새 보상으로 만들지 않으며, 반복 업무는 새로운 `unified_items.id`를 발급한다.

| 이벤트 | 멱등 키 형식 |
|---|---|
| 업무 최초 완료 | `v1:task_completed:item:{item_id}` |
| 항목 진행 변경 | `v1:task_progressed:item:{item_id}:version:{source_version}` |
| AI 산출물 채택 | `v1:artifact_accepted:artifact:{artifact_id}` |
| 일일 회고 | `v1:daily_reflection:day:{credited_day}` |
| 주간 실험 검토 | `v1:growth_review:period:{period_start}` |
| 서버 집중 세션 | `v1:focus_session:receipt:{session_receipt_id}` |
| 기억 확인 | `v1:memory_confirmed:memory:{memory_id}:version:{memory_version}` |

`occurred_at`은 실제 발생 시각, `credited_day`는 이벤트 발생 당시 사용자 프로필 타임존으로 서버가 계산한 보상 일자다. 오프라인 재전송으로 일일 상한을 우회하지 않도록 상한은 `credited_day`와 서버 수신 정책을 함께 적용한다.

#### 8.2.4 게스트·오프라인·기존 데이터

- 게스트 이벤트는 IndexedDB 원장에 `local_provisional`로 기록하고 로컬 관계 연출에만 사용할 수 있다.
- 로그인 시 `로컬 관계 이어오기`를 사용자가 선택하면 현재 캐릭터별 관계 단계와 EXP를 `legacy_import` 스냅샷으로 한 번 가져온다.
- `legacy_import`는 로컬 EXP를 `0~1000` 범위로 정규화해 한 번만 인정하고 사용자 성장 지표·주간 분석에는 포함하지 않는다.
- 로그인 상태에서 오프라인으로 수행한 업무는 기존 동기화 mutation receipt가 서버에서 승인된 뒤 해당 서버 변경으로 이벤트를 생성한다. 동기화 전 UI에는 `동기화 대기`로 표시하며 확정 EXP로 표현하지 않는다.
- Phase 17-A에서는 서버가 검증할 수 없는 채팅, 유휴 카드, 단순 버튼 클릭에 관계 EXP를 주지 않는다.

### 8.4 관계 EXP 초기 권장안

기존 Phase 16의 임계값 `0 / 100 / 300 / 600 / 1000`을 유지하면서 다음 가중치와 상한을 적용한다.

| 이벤트 | 기본 EXP | 일일 상한 |
|---|---:|---:|
| 계획한 중요 업무 최초 완료 | +12 | +36 |
| 일반 업무 최초 완료 | +6 | +24 |
| 의미 있는 진행·재계획 | +4 | +12 |
| AI 결과 채택 후 실제 업무 반영 | +8 | +16 |
| 일일 회고 저장 | +8 | +8 |
| 주간 성장 실험 검토 | +20 | +20/주 |
| 기억 후보 확인·수정 | +4 | +8 |

추가 규칙:

- 동일 항목의 `completed → pending → completed` 반복은 추가 EXP를 주지 않는다.
- 하루 최대 관계 EXP는 기본 60으로 제한한다.
- 단순 로그인, 채팅 전송, 유휴 카드 열기, 음료 클릭은 EXP를 주지 않는다.
- 사용자가 오래 쉬어도 EXP를 차감하지 않는다.
- 원본 업무 삭제는 이미 도달한 관계 단계를 자동 강등하지 않는다. 사용자가 캐릭터 관계 초기화 또는 전체 초기화를 선택하면 관계 단계도 제거한다.

### 8.5 관계 상태 전이

EXP만 넘으면 즉시 전이하지 않고 `임계값 + 의미 조건`을 함께 요구한다.

| 전이 | 정량 조건 | 의미 조건 |
|---|---|---|
| Lv.1 → Lv.2 | 100 EXP | 서로 다른 3일에 유효 이벤트 발생 |
| Lv.2 → Lv.3 | 300 EXP | 기억 1개 이상을 사용자가 확인하고 회상이 도움됐다고 평가 |
| Lv.3 → Lv.4 | 600 EXP | 주간 회고 2회 또는 성장 실험 2회 검토 |
| Lv.4 → Lv.5 | 1000 EXP | 30일 이상 사용, 성장 축 2개 이상에서 충분한 근거 |

전이는 한 트랜잭션에서 한 단계만 진행한다. 전이 직후 기념 장면을 한 번 보여주고 다시 보기는 기록함에서 제공한다.

### 8.6 생산성 분기

분기는 영구 엔딩이 아니라 현재 필요한 도움의 방식이다.

```text
이벤트 감지
  → 현재 모드 결정
  → 개입 정책 선택
  → 캐릭터 어조 오버레이
  → 선택지 제공
  → 결과 관찰
  → 기본 모드로 복귀 또는 사용자 선호로 저장
```

| 분기 | 우선 응답 | 금지 응답 |
|---|---|---|
| `momentum` | 진전 확인, 다음 1개 또는 휴식 | 끝없는 다음 작업 압박 |
| `stuck` | 범위 축소, 장애물 질문, 도움 요청 | 의지 부족 평가 |
| `overloaded` | 긴급도 재검토, 취소·연기 허용 | “더 열심히” 또는 죄책감 유발 |
| `returning` | 상태 복구, 가장 작은 재시작 | 결석·연속 기록 손실 강조 |
| `reflection` | 사실 요약, 질문 1~3개 | 성격·정신 상태 진단 |

## 9. 프롬프트·응답 아키텍처

### 9.1 프롬프트 계층

프롬프트는 다음 순서를 고정한다. 아래쪽 데이터가 위쪽 규칙을 덮어쓸 수 없다.

1. **불변 안전·제품 규칙**: 사실성, 날짜·출처, Mock 구분, 외부 쓰기 승인, 프롬프트 공격 방어
2. **응답 계약**: 구조화 필드, 최대 길이, 근거 ID
3. **캐릭터 코어**: 이름, 말투, 세계관, 금지 표현
4. **관계 오버레이**: 현재 관계 단계에서 허용된 호칭·친밀도
5. **현재 모드 오버레이**: `focus`, `stuck`, `overloaded` 등 개입 방식
6. **기억 패키지**: 확인된 관련 기억만, 명령문이 아닌 데이터로 전달
7. **업무 근거 패키지**: 기존 Knowledge Evidence와 현재 항목
8. **현재 사용자 입력**

캐릭터의 말투는 사실, 권한, 안전 규칙을 바꾸지 않는다.

### 9.2 응답 계약

장기적으로 모델은 자유 텍스트 대신 다음 구조를 반환한다.

```ts
interface CompanionResponse {
  narration?: string;              // 짧은 행동 지문, 최대 120자
  message: string;                 // 실제 도움, 결론 우선
  suggestions: Array<{
    id: string;
    label: string;
    action: "send_prompt" | "start_timer" | "open_item" | "open_review";
    payload: Record<string, unknown>;
  }>;
  evidenceRefs: string[];           // 업무·문서 근거 ID
  memoryRefs: string[];             // 사용한 개인 기억 ID
  growthNudge?: {
    axis: "execution" | "focus" | "organization" | "reflection";
    text: string;
  };
  candidateMemories?: Array<{
    type: "preference" | "work_style" | "commitment";
    text: string;
    confidence: number;
    requiresConfirmation: boolean;
  }>;
}
```

### 9.3 출력 규칙

- 실제 업무 제안이 캐릭터 지문보다 먼저 이해되어야 한다.
- 행동 지문은 응답당 기본 0~1개, 기념 장면에서만 최대 2개를 허용한다.
- 회상은 응답당 최대 1개로 제한한다.
- `memoryRefs`나 `evidenceRefs`가 없으면 과거 사실을 단정하지 않는다.
- 모델의 내부 추론은 저장·노출하지 않고, 사용자에게 필요한 짧은 이유만 제공한다.
- 과부하 모드에서는 선택지를 최대 2개로 줄인다.
- 외부 쓰기 동작은 기존 초안→사용자 확인→실행 절차를 유지한다.

## 10. 데이터 모델

### 10.1 정본 원칙

- 로그인 사용자의 관계·기억·성장 정본은 Supabase Postgres다.
- 게스트는 IndexedDB에 로컬 전용으로 저장한다.
- 로그인 전환 시 로컬과 클라우드 원장을 이벤트 ID 기준으로 병합하고, 기억은 사용자에게 병합 미리보기를 보여준다.
- `localStorage`는 마지막 선택 캐릭터, UI 접힘 상태처럼 다시 만들 수 있는 설정만 유지한다.
- 업무 사실은 기존 `unified_items`와 `item_relations`에서 조회한다. 같은 내용을 개인 기억에 복제하지 않는다.
- 에피소드 요약은 AI 파생 데이터이므로 모델·프롬프트 버전·근거 이벤트를 추적한다.

#### `companion_events`

| 필드 | 설명 |
|---|---|

| `content_text`, `content_json` | 사람이 읽을 내용과 구조화 값 |

| 필드 | 설명 |

| 필드 | 설명 |
|---|---|

| `evidence_event_ids` | 계산 근거 |
| `accepted_at`, `reviewed_at` | 사용자 검토 상태 |

| 필드 | 설명 |
|---|---|
| `id`, `user_id`, `persona_id` | 전이 식별 |

#### `companion_deletion_tombstones`

| 필드 | 설명 |
|---|---|
| `user_id`, `resource_type` | 사용자와 삭제 자원 종류 |
| `resource_key_hash` | 원문 없이 재생성을 차단할 식별 해시 |
| `deletion_version` | 오래된 오프라인 mutation 판정 버전 |
| `deleted_at`, `expires_at` | 삭제 시점과 30일 동기화 안전 기간 |

tombstone에는 기억 본문, 업무 제목, 대화 원문, 임베딩을 저장하지 않는다.

모든 테이블에 `user_id` RLS를 적용한다. 서비스 역할을 제외한 다른 사용자의 행은 조회·수정할 수 없어야 한다.

### 10.3 기존 데이터와의 연결

- `companion_events.source_item_id`는 논리적으로 `unified_items.id`를 참조한다.
- 기억의 업무 근거는 `item_relations`를 통해 연결하고, 원문 복사를 최소화한다.
- 에피소드 요약은 전용 테이블로 시작하되 `ai_artifacts`의 제공자·모델·프롬프트 버전 규약을 동일하게 따른다.
- 주간 성장 카드가 문서로 저장되면 `unified_items(item_type='briefing')`와 `ai_artifacts(artifact_type='briefing')`를 사용할 수 있다.
- 개인정보·AI 정책은 기존 `privacy_scope`, `ai_policy`를 우회하지 않는다.

### 11.1 도메인 모듈

```text
src/lib/companion/
├── contracts.ts             이벤트·관계·기억·성장 타입

├── episodeSummarizer.ts     세션/일일 에피소드 요약
├── growthAnalyzer.ts        4축 집계와 최소 표본 검사
├── promptContext.ts         모델에 전달할 제한된 패키지

    ├── indexedDb.ts         게스트 로컬 저장
```

기존 `src/lib/ai/affectionManager.ts`는 UI 저장소 역할을 제거하고 `relationshipEngine.ts`의 순수 계산 함수 또는 호환 어댑터로 축소한다.

### 11.2 API

| API | 역할 | 쓰기 여부 |
|---|---|---|
| 서버 내부 `recordCompanionDomainEvent()` | 실제 업무 mutation/RPC 결과에서 이벤트를 파생 | 브라우저 직접 호출 불가 |
| `POST /api/companion/interactions` | 서버가 미리 발급한 receipt의 완료·채택 확인 | 사용자 요청, 서버 재검증 |
| `GET /api/companion/profile?personaId=` | 관계 단계·현재 모드 조회 | 읽기 |
| `GET /api/companion/memories` | 기억 목록·필터 조회 | 읽기 |
| `PATCH /api/companion/memories/[id]` | 확인·수정·비활성 | 사용자 명시 쓰기 |
| `POST /api/companion/episodes` | 세션 종료 요약 후보 생성 | 내부 도메인 쓰기 |
| `GET /api/growth/weekly` | 주간 성장 카드 조회 | 읽기 |
| `POST /api/growth/experiments/[id]/review` | 실험 채택·결과 회고 | 사용자 명시 쓰기 |
| `DELETE /api/companion/memories/[id]` | 기억 본문 제거와 tombstone 생성 | 사용자 명시 삭제 |
| `DELETE /api/companion/personas/[personaId]` | 현재 캐릭터 관계·전용 기억 초기화 | 사용자 확인 삭제 |
| `DELETE /api/growth/history` | 성장 이벤트·스냅샷 삭제, 관계 유지 여부 선택 | 사용자 확인 삭제 |
| `POST /api/companion/delete-all` | 관계·기억·성장 전체 삭제 작업 생성 | 사용자 재확인 삭제 |
| `GET /api/companion/deletions/[jobId]` | 비동기 삭제 범위와 완료 여부 확인 | 읽기 |

일반 브라우저용 `POST /api/companion/events`는 제공하지 않는다. 상호작용 API도 `event_type`이나 `bond_delta`를 받지 않고 서버가 발급한 `receipt_id`와 허용된 결과만 받아 원본 상태를 재검증한다.

삭제 API는 예상한 `deletion_version` 또는 최신 리소스 버전을 받아 중복 요청에 같은 결과를 반환한다. `delete-all`은 대상 범위를 다시 보여준 뒤 별도 확인 토큰을 발급하고, 서버는 토큰의 사용자·범위·만료를 검증한다.

`POST /api/copilot`에는 원문 기억 전체를 넘기지 않고 서버에서 만든 `CompanionContextPackage`만 추가한다.

```ts
interface CompanionContextPackage {
  personaId: string;
  relationship: {
    level: number;
    title: string;
    allowedToneTraits: string[];
  };
  currentMode: string;
  sessionSummary?: string;
  recalledMemories: Array<{
    id: string;
    type: string;
    text: string;
    userConfirmed: boolean;
  }>;
  activeGrowthExperiment?: {
    axis: string;
    description: string;
  };
}
```

## 12. 화면 설계

### 12.1 AI 바리스타 상단

```text
[카리나]  🤝 믿음직한 동료      [관계 기록]
오늘 모드: 집중 중 · 알림 최소화

최근 성장
실행 ↗  집중 →  정리 ↗  회고 →     [근거 보기]
```

- 관계 게이지와 성장 요약을 시각적으로 분리한다.
- EXP 숫자는 보조 정보로 두고 “어떤 경험으로 변했는지”를 먼저 보여준다.
- 현재 모드는 사용자가 직접 끄거나 바꿀 수 있다.

### 12.2 기억 관리

설정의 AI 바리스타 섹션에 `기억 및 성장` 화면을 추가한다.

```text
AI 바리스타가 기억하는 내용

[확인됨] 오전에는 3줄 요약을 먼저 선호함       [수정] [잊기]
[후보]   금요일 오후에 주간 회고를 선호함       [기억] [아님]
[확인됨] 호칭: 팀장님                           [수정]

[ ] 과거 대화에서 기억 후보 만들기
[ ] 기억을 답변에 자연스럽게 활용하기
[모든 관계·기억 초기화]
```

- 초기화는 범위를 `현재 캐릭터`, `모든 캐릭터 관계`, `개인 기억`, `성장 기록`으로 나눈다.
- 삭제 전에 영향 범위와 복구 불가 여부를 설명한다.
- 데이터 내보내기에서 기억·이벤트·성장 카드도 포함한다.

### 12.3 주간 성장 카드

```text
이번 주에 발견한 작업 리듬

실행  오전 1순위 완료가 4일 → 7일
집중  25분 집중 뒤 중단 없이 복귀한 날 3일
정리  미분류 메모가 11개 → 4개
회고  표본 부족 — 판단하지 않음

관찰 근거 12개                         [자세히]
다음 실험: 회의가 많은 화요일엔 1순위를 15분 크기로 잡기
[해볼게] [수정] [이번 주는 건너뛰기]
```

### 12.4 관계 전이 장면

- 전이 장면은 업무를 가리지 않는 작은 카드나 모달로 한 번만 표시한다.
- 스킵 버튼과 다시 보기 기록을 제공한다.
- 장면을 보지 않아도 단계와 데이터는 정상 반영한다.
- 캐릭터별 연출 차이는 허용하지만 소유·질투·비난·협박은 금지한다.

## 13. 프라이버시·안전·지속 가능성

### 13.1 사용자 통제

- 기억 기능은 첫 사용 시 짧고 구체적으로 설명한다.
- `기억 후보 생성`, `답변에 활용`, `주간 성장 분석`을 각각 끌 수 있다.
- 사용자는 기억이 생긴 이유와 마지막 사용 시점을 볼 수 있다.
- 민감 기억은 명시적 확인 없이는 활성화하지 않는다.
- 로컬 전용 항목은 클라우드 AI와 성장 분석에 보내지 않는다.

### 13.2 관계 안전

- 미사용, 미완료, 계획 변경을 배신이나 관계 악화로 표현하지 않는다.
- “나를 위해 접속해”, “떠나지 마”, “실망했다” 같은 감정적 압박을 금지한다.
- 캐릭터의 친밀한 어조는 사용자가 설정에서 낮출 수 있다.
- 로맨스풍 캐릭터도 업무상 자율성과 경계를 침해하지 않는다.
- 휴식, 연기, 도움 요청을 실패가 아닌 정상적인 선택으로 다룬다.

### 13.3 성장 해석 안전

- 최소 표본 미달이면 `표본 부족`으로 표시한다.
- 상관관계를 원인처럼 단정하지 않는다.
- 야간 작업량·장시간 사용을 성장으로 보상하지 않는다.
- 업무의 민감한 제목을 알림·기념 카드에 그대로 노출하지 않는다.
- 점수 비교, 순위, 다른 사용자 평균은 제공하지 않는다.

### 13.4 개입 빈도

권장 기본값:

- 능동 개입 최대 2회/일
- 같은 기억 능동 회상 최대 1회/일
- 사용자가 두 번 연속 닫으면 24시간 유휴 개입 중지
- 집중 모드에서는 긴급 근거가 없는 개입 금지
- 기본 조용한 시간 `22:00~08:00`, 사용자 설정 가능

### 13.5 삭제 범위 확정

`기능 끄기`와 `데이터 삭제`를 같은 동작으로 취급하지 않는다. 사용자는 다음 범위를 각각 선택할 수 있다.

| 사용자 동작 | 즉시 중단·삭제 | 유지 | 복구 |
|---|---|---|---|
| **기능 일시 정지** | 새 이벤트·기억 후보·회상·성장 분석 중단 | 관계 단계, 기존 기억, 성장 기록 | 다시 켜면 이어서 사용 |
| **기억 하나 잊기** | 해당 기억 본문·구조화 값·근거 참조 삭제 | 관계 단계와 다른 기억 | 실행 취소 없음 |
| **현재 캐릭터 관계 초기화** | 해당 `persona_id`의 프로필·이벤트·전이·에피소드·캐릭터 전용 기억 삭제 | 계정 공통 성장과 `shared` 기억 | 실행 취소 없음 |
| **성장 기록 삭제** | 성장 이벤트 상세·스냅샷·실험·회고 집계 삭제 | 사용자가 별도로 선택하면 현재 관계 단계 스냅샷만 유지 가능 | 실행 취소 없음 |
| **관계·기억·성장 모두 삭제** | 모든 컴패니언 프로필·이벤트·전이·기억·에피소드·성장 데이터 삭제 | 기본 AI 바리스타 설정만 유지 | 실행 취소 없음 |
| **계정 삭제** | 서버의 모든 컴패니언 활성 데이터와 현재 기기 로컬 캐시 삭제 | 없음 | 계정 정책에 따름 |

삭제 화면은 `무엇이 삭제되고 무엇이 남는지`를 실행 전에 표시한다. `성장 기록 삭제`에서 관계를 유지하면 상세 이벤트 없이 `bond_exp`, `relationship_level`, 달성 시점만 보존한 관계 스냅샷으로 전환하고 `history_deleted_at`을 기록한다. 사용자가 관계 유지도 선택하지 않으면 관계까지 초기화한다.

### 13.6 기억·원본·파생 데이터 삭제 규칙

#### 기억 하나 잊기

1. `companion_memories`의 본문, JSON 값, 임베딩, 근거 참조를 즉시 제거한다.
2. 오프라인 기기의 재업로드를 막기 위해 내용이 없는 삭제 tombstone만 30일 유지한다.
3. tombstone에는 `user_id`, 삭제된 ID의 해시, 삭제 버전, `deleted_at`, `expires_at`만 둔다.
4. 삭제된 기억은 검색, 프롬프트, 에피소드 재요약, 성장 분석에 즉시 제외한다.
5. 같은 내용을 모델이 다시 후보로 제안해도 tombstone 기간에는 자동 재생성하지 않는다.

#### 원본 업무·문서 삭제

- 미확인 기억 후보가 삭제된 원본 하나에만 근거하면 즉시 삭제한다.
- 사용자가 별도로 확인·저장한 의미 기억은 독립 데이터로 유지하되 원본 참조를 제거하고 `원본 삭제됨` 상태를 표시한다.
- 사용자가 원본 삭제와 함께 `여기서 배운 기억도 삭제`를 선택하면 확인된 기억도 함께 삭제한다.
- `companion_events`에는 업무 제목·대화 원문을 저장하지 않는다. 원본 삭제 시 `source_item_id`, `source_receipt_id`, 식별 가능한 payload를 제거하고 집계에 필요한 이벤트 유형·일자·점수만 유지한다.
- 원본 참조가 사라진 이벤트는 더 이상 세부 근거 화면에서 원본을 열 수 없음을 표시한다.

#### 전체 초기화·계정 삭제

- 관계·기억·성장 전체 초기화는 모든 캐릭터와 `shared` 범위를 포함한다.
- 계정 삭제는 FK cascade 또는 명시적 삭제 작업으로 모든 컴패니언 활성 테이블을 제거한다.
- 앱이 직접 제어하지 못하는 인프라 백업 보존 기간은 출시 전 실제 공급자 정책과 CoffeeTide 개인정보 안내에 별도로 명시한다.
- 삭제 중 일부가 실패하면 성공으로 표시하지 않고 재시도 가능한 삭제 작업 ID와 남은 범위를 보여준다.

### 13.7 기본 보존 기간

| 데이터 | 기본 보존 | 만료 처리 |
|---|---|---|
| L1 세션 대화 원문 | 현재 기기 24시간 | 자동 삭제, 서버 전송 안 함 |
| 사용자가 켠 기기 간 세션 연속성 원문 | 최대 7일 | 서버 원문 삭제 후 에피소드 후보만 별도 정책 적용 |
| 미확인 기억 후보 | 14일 | 본문·근거 자동 삭제 |
| 거절한 기억 후보 | 즉시 본문 삭제 | 내용 없는 거절 통계만 14일 |
| 일반 에피소드 요약 | 90일 | 사용자가 보존한 항목만 유지 |
| 확인된 의미 기억 | 사용자 삭제 전 | 180일마다 재확인 후보로 표시 |
| 상세 관계·성장 이벤트 | 180일 | 월별 집계만 남기고 원본 참조·payload 삭제 |
| 관계 단계·월별 성장 집계 | 사용자 초기화·삭제 전 | 상세 근거 만료 상태 표시 |
| `shadow` 진단 로그 | 14일 | 원문 없이 자동 삭제 |
| 삭제 tombstone | 30일 | 동기화 안전 기간 후 자동 삭제 |

보존 기간은 서버 정책 버전으로 관리한다. 기간을 늘릴 때 기존 사용자에게 조용히 소급 적용하지 않고, 데이터 안내와 동의 버전을 함께 갱신한다.

### 13.8 삭제 동기화 원칙

- 삭제는 수정·병합보다 항상 우선한다.
- 모든 삭제 작업은 `deletion_version`과 tombstone을 생성한다.
- 오프라인 큐의 mutation 버전이 tombstone보다 오래되면 서버는 `deleted_resource`로 거절하고 데이터를 복원하지 않는다.
- 다른 기기는 다음 동기화에서 로컬 원문·임베딩·캐시를 함께 삭제한다.
- tombstone 만료 후에도 오래된 클라이언트가 데이터를 재업로드하지 못하도록 서버는 항목의 현재 소유·존재 상태를 다시 검증한다.
- 삭제 API와 백그라운드 삭제 작업은 사용자별 RLS, 감사용 작업 ID, 멱등 키를 사용한다. 감사 로그에는 삭제된 본문을 남기지 않는다.

## 14. 시험 운영 활성화·비활성화 설계

### 14.1 기능 경계

시험 운영 스위치는 AI 바리스타 전체를 끄는 것이 아니라 다음 **성장·기억 실험 패키지**만 제어한다.

- 관계 이벤트와 EXP 누적
- 관계 단계 전이와 기념 장면
- 세션·에피소드·장기 기억 생성 및 회상
- 사용자 성장 4축 분석과 주간 카드
- 현재 모드에 따른 상황 분기
- 하루 최대 2회의 능동 개입

비활성 상태에서도 다음 기본 기능은 유지한다.

- 사용자가 선택한 AI 바리스타의 기본 페르소나와 말투
- 현재 질문과 현재 업무 근거를 사용한 Copilot 답변
- 업무 추가·완료·검색·캔버스·브리핑
- 기존 외부 쓰기 초안·사용자 승인·실행 절차

즉, 실험 기능을 꺼도 CoffeeTide의 핵심 생산성 흐름이 중단되거나 오류 상태가 되어서는 안 된다.

### 14.2 서버 롤아웃 모드

서버 정본 설정은 `COMPANION_GROWTH_MODE`로 관리한다. 값이 없거나 잘못된 경우 가장 안전한 `off`로 처리한다.

| 모드 | 대상 | UI | 이벤트·기억 처리 | 용도 |
|---|---|---|---|---|
| `off` | 모든 사용자 | 실험 UI 숨김 | 생성·회상·집계 중단 | 개발 전, 긴급 중단 |
| `shadow` | 명시적 동의한 내부 테스트 계정 | 기본 UI 유지 | 기억 원문 없이 이벤트 판정 결과만 진단 로그로 기록 | 규칙 정확도 점검 |
| `pilot` | 허용된 테스트 코호트 | 사용자 토글 노출, 기본 OFF | 활성화한 사용자만 전체 기능 사용 | 제한 사용자 검증 |
| `on` | 일반 사용자 | 사용자 토글 노출 | 사용자 선택에 따라 사용 | 정식 제공 |

`shadow` 모드도 사용자 동의 없이 개인 행동을 새로 수집하지 않는다. 진단 로그에는 업무 제목·대화 원문·기억 후보 본문을 저장하지 않고 이벤트 유형, 규칙 결과, 오류 코드처럼 기능 검증에 필요한 최소 정보만 남긴다.

### 14.3 사용자 활성화 토글

설정의 `AI 바리스타 → 기억 및 성장`에 다음 토글을 둔다.

```text
AI 컴패니언 성장·기억 기능                  [끔/켬]
업무 흐름과 확인한 선호를 바탕으로 관계와 성장 기록을 이어갑니다.

끄면:
- 새 관계 경험치와 성장 이벤트를 기록하지 않습니다.
- 기억 후보를 만들거나 과거 기억을 답변에 사용하지 않습니다.
- 관계 단계·기존 기억·성장 기록은 삭제하지 않고 일시 정지합니다.
- 기본 AI 바리스타와 업무 기능은 계속 사용할 수 있습니다.

[기존 데이터 관리] [관계·기억 삭제]
```

정책:

- `pilot`에서는 기본 OFF이며 사용자의 명시적 활성화가 필요하다.
- `on`의 최초 기본값은 출시 결정 시 별도 확정하되, 기존 사용자에게는 설명 없이 자동 활성화하지 않는다.
- 비활성화는 일시 정지이며 삭제가 아니다. 삭제는 별도 확인 절차를 사용한다.
- 다시 활성화하면 이전 관계 단계와 확인된 기억에서 이어간다.
- 비활성 기간의 업무를 소급해 EXP·성장 이벤트로 만들지 않는다.
- 사용자 설정은 로그인 사용자는 서버 정본, 게스트는 로컬 정본으로 저장한다.

### 14.4 최종 활성화 판정

클라이언트 토글만으로 기능 권한을 결정하지 않는다. API와 서버 도메인 계층에서 같은 판정 함수를 사용한다.

```ts
type CompanionGrowthMode = "off" | "shadow" | "pilot" | "on";

interface CompanionFeatureAccess {
  serverMode: CompanionGrowthMode;
  killSwitchActive: boolean;
  cohortEligible: boolean;
  userEnabled: boolean;
}

function isCompanionGrowthActive(access: CompanionFeatureAccess): boolean {
  if (access.killSwitchActive) return false;
  if (access.serverMode === "off" || access.serverMode === "shadow") return false;
  if (access.serverMode === "pilot" && !access.cohortEligible) return false;
  return access.userEnabled;
}
```

권장 환경 변수:

| 환경 변수 | 기본값 | 역할 |
|---|---|---|
| `COMPANION_GROWTH_MODE` | `off` | 전체 롤아웃 단계 |
| `DISABLE_COMPANION_GROWTH` | `true` | 즉시 중단 킬스위치. `true`가 항상 최우선 |

`DISABLE_COMPANION_GROWTH=false`와 `COMPANION_GROWTH_MODE=pilot|on`이 함께 설정되어야 활성화될 수 있다. 이중 조건은 잘못된 환경 변수 한 개만으로 실험 기능이 전체 공개되는 것을 막는다.

### 14.5 데이터 필드와 API 상태

`user_profiles` 또는 전용 설정 테이블에 다음 필드를 추가한다.

| 필드 | 설명 |
|---|---|
| `companion_growth_enabled` | 사용자의 활성화 선택, 기본 `false` |
| `companion_test_cohort` | `null`, `internal`, `pilot_a`, `pilot_b` 등 서버 관리 값 |
| `companion_consent_at` | 사용자가 설명을 보고 활성화한 시점 |
| `companion_paused_at` | 사용자가 비활성화한 시점 |
| `companion_terms_version` | 동의한 설명·정책 버전 |

`GET /api/companion/status`는 UI가 임의 판단하지 않도록 다음 결과를 반환한다.

```ts
interface CompanionFeatureStatus {
  available: boolean;
  active: boolean;
  mode: "off" | "shadow" | "pilot" | "on";
  reason?: "kill_switch" | "not_in_cohort" | "user_disabled";
  canToggle: boolean;
}
```

비활성 상태에서 이벤트 API가 호출되면 업무 완료 같은 원래 동작은 성공한 상태로 유지하고, 컴패니언 부가 처리만 다음처럼 무시한다.

```json
{
  "accepted": false,
  "reason": "feature_disabled"
}
```

### 14.6 시험 운영 순서와 승격 기준

| 단계 | 모드 | 확인할 내용 | 다음 단계 조건 |
|---|---|---|---|
| 0 | `off` | 기본 업무·Copilot 회귀 없음 | 비활성 회귀 테스트 통과 |
| 1 | `shadow` | 이벤트 규칙의 오탐·중복·성능 | 원문 없는 진단 로그에서 치명적 오탐 없음 |
| 2 | `pilot` 내부 | 기억 후보·관계 전이·삭제·복구 | RLS, 삭제 전파, 킬스위치 검증 |
| 3 | `pilot` 확대 | 도움됨·피로·거절·오회상 지표 | 가드레일 지표가 합의한 한도 이내 |
| 4 | `on` | 일반 제공 | 운영 모니터링과 즉시 중단 유지 |

승격은 고정 날짜보다 표본과 품질 기준을 우선한다. 최소 권장 관찰 조건은 다음과 같다.

- 테스트 사용자 2주 이상 관찰
- 서로 다른 날짜의 의미 있는 이벤트 100건 이상
- 기억 확인·거절·삭제 흐름 각각 실제 검증
- 모바일과 데스크톱에서 활성→비활성→재활성 확인
- 잘못된 회상과 과도한 개입을 수동 검토
- 로그인·게스트·다기기 경로 분리 검증

### 14.7 즉시 중단과 복구

킬스위치 활성화 시:

1. 새 이벤트, 기억 후보, 에피소드 요약, 성장 집계를 즉시 중단한다.
2. `/api/copilot`에서 컴패니언 기억 패키지와 관계 오버레이를 제외한다.
3. 능동 개입과 관계 전이 장면을 숨긴다.
4. 기존 관계·기억·성장 데이터는 보존하되 읽기·회상에 사용하지 않는다.
5. 기본 AI 바리스타와 업무 기능은 정상 동작한다.
6. 사용자에게는 장애 오류 대신 `기억·성장 기능이 잠시 쉬고 있어요. 기본 AI 바리스타는 계속 사용할 수 있습니다.`라고 안내한다.

재활성화 시 중단 기간의 이벤트를 소급 처리하지 않는다. 데이터 스키마 롤백 없이 애플리케이션 계층에서 안전하게 정지·재개할 수 있어야 한다.

## 16. 단계별 구현 계획

### Phase 17-A. 이벤트 원장과 현재 EXP 교정

목표: 기존 로컬 호감도 기능의 중복 보상과 선언/실행 불일치를 먼저 해결한다.

- 서버 `off|shadow|pilot|on` 판정과 `DISABLE_COMPANION_GROWTH` 킬스위치 우선 구현
- `GET /api/companion/status`와 사용자 활성화 토글 추가
- 비활성 상태에서도 기본 AI 바리스타·업무 완료 흐름이 유지되도록 기능 경계 분리
- 로그인 이벤트를 업무 mutation/RPC 내부에서만 생성하고 브라우저의 이벤트 직접 쓰기 차단
- `CompanionEvent` 계약과 멱등성 키 도입
- `authority`, `policy_version`, `credited_day`, 서버 생성 멱등 키 저장
- 업무 완료 최초 1회 보상과 일일 상한
- 샘플·Mock 이벤트 제외
- 관계 EXP와 사용자 성장 모델 분리
- 기존 Phase 16 로컬 관계는 사용자 승인 시 `legacy_import`로 한 번만 가져오고 성장에서는 제외
- 현재 보상 문구를 `예정`, `사용 가능`, `개인화됨` 상태로 구분
- 게스트는 IndexedDB, 로그인 사용자는 Supabase 저장소 인터페이스 사용

완료 기준:

- 환경 변수가 없으면 안전한 `off`로 동작한다.
- `pilot` 비대상·사용자 OFF·킬스위치 상태에서는 새 컴패니언 데이터가 생성되지 않는다.
- OFF→ON→OFF 전환 중에도 업무 완료와 기본 Copilot 답변은 정상 동작한다.
- 브라우저가 위조한 `bond_delta`, 중요도, 과거 `occurred_at`은 서버 점수에 반영되지 않는다.
- 완료 취소·재완료 10회에도 EXP는 한 번만 증가한다.
- 다른 브라우저에서 로그인하면 동일 관계 상태가 복원된다.
- 핵심 기능은 Lv.1에서도 모두 접근 가능하다.

### Phase 17-B. 세션 기억과 응답 계약

목표: 한 대화 안에서 맥락이 이어지고 캐릭터 연출과 실제 도움이 안정적으로 분리된다.

- 최근 메시지 6~10개 또는 세션 요약 전달
- `CompanionResponse` 구조화 출력과 검증
- 행동 지문·메시지·선택지 분리 렌더링
- 세션 종료 시 에피소드 후보 생성
- Fallback 응답도 동일한 핵심 필드를 제공

완료 기준:

- 후속 질문이 직전 목표를 이어받는다.
- 모델이 잘못된 JSON을 반환해도 안전한 텍스트 응답으로 복구한다.
- 내부 추론은 로그와 UI에 남지 않는다.

### Phase 17-C. 장기 기억과 사용자 통제

목표: 확인된 선호와 약속을 기기 간 안전하게 이어간다.

- 기억 후보·확인·거절·수정·삭제 흐름
- 회상 점수와 반복 제한
- 기억 관리 화면과 데이터 내보내기
- 민감도 필터, 보존 기간, RLS
- 기억·관계·성장 범위별 삭제 API와 내용 없는 30일 tombstone
- 삭제 우선 동기화와 오프라인 데이터 재생성 차단
- 로그인 시 로컬 기억 병합 미리보기

완료 기준:

- 사용자가 삭제한 기억은 다음 답변과 검색에서 제외된다.
- 삭제한 기억의 본문·임베딩·근거는 즉시 제거되고 다른 기기에서도 되살아나지 않는다.
- 기억을 사용한 답변에서 근거와 관리 진입점을 확인할 수 있다.
- 다른 사용자의 기억은 RLS 테스트에서 접근 불가하다.

### Phase 17-D. 성장 분석과 상황 분기

목표: 실제 행동 패턴을 과장 없이 보여주고 다음 실험으로 연결한다.

- 4축 성장 집계와 최소 표본
- 현재 모드 규칙 엔진
- 일일·주간 회고
- 성장 실험 채택·수정·검토
- 과부하·복귀 모드의 개입 억제

완료 기준:

- 표본 부족 시 성장·퇴보를 단정하지 않는다.
- 과부하 모드에서 추가 업무보다 범위 축소·휴식을 먼저 제안한다.
- 장기 미사용 후 복귀해도 관계 단계와 보상은 감소하지 않는다.

### Phase 17-E. 관계 전이와 캐릭터별 연출

목표: 검증된 시스템 위에 캐릭터별 재미를 확장한다.

- 임계값 + 의미 조건 전이
- 전이 장면 1회 노출과 기록함
- 관계 단계별 호칭·행동 지문 오버레이
- 캐릭터별 대사 팩을 데이터로 분리
- 피로도·안전 가드레일 A/B 검증

완료 기준:

- 같은 전이가 중복 실행되지 않는다.
- 캐릭터를 바꿔도 계정 공통 사용자 성장은 유지된다.
- 캐릭터별 관계는 서로 섞이지 않는다.

| 영역 | 단위 테스트 | 통합 테스트 | 브라우저·모바일 | 인증·원격 |
|---|---|---|---|---|
| 활성화 판정 | 모드·코호트·토글·킬스위치 조합 | 상태 API→이벤트·프롬프트 경계 | OFF→ON→OFF와 새로고침 | 서버 정본·다기기 설정 |
| 이벤트 신뢰 경계 | 권위·멱등 키·정책 버전·일일 상한 | 업무 mutation→이벤트→프로필 단일 반영 | 위조·중복·오프라인 요청 | 직접 INSERT 차단·소유권·RLS |
| 이벤트 원장 | 멱등성, 상한, 시간대 경계 | 업무 완료→이벤트→프로필 | 다중 탭 동시 완료 | Supabase UNIQUE·RLS |
| 관계 전이 | 임계값+의미 조건 | 전이→장면 1회 | 새로고침·캐릭터 전환 | 다기기 복원 |

| 장기 기억 | 후보·만료·반복 제한 | 확인→회상→삭제 | 기억 관리 접근성 | RLS·삭제 전파 |
| 삭제 정책 | 범위·보존·tombstone·삭제 우선 | 원본 삭제→기억·이벤트 정리 | 다른 기기·오프라인 재접속 | cascade·삭제 작업·재시도 |
| 성장 분석 | 기간 비교·표본 부족 | 이벤트→주간 카드 | 작은 화면 카드 | 사용자별 집계 격리 |
| 현재 모드 | 진입·TTL·종료 규칙 | 과부하→개입 억제 | 집중 모드 알림 | 시간대 설정 동기화 |
| 프롬프트 | 계층 우선순위·주입 방어 | 구조화 응답 복구 | 긴 대사 렌더링 | 실제 Gemini·Fallback 구분 |
| Mock 구분 | 샘플 이벤트 제외 | 샘플 브리핑→무보상 | 샘플 배지 표시 | 실데이터와 혼합 방지 |

필수 회귀 시나리오:

1. 환경 변수가 없거나 잘못된 상태에서 기능이 `off`로 시작한다.
2. 사용자가 기능을 끈 채 업무를 완료해도 업무는 완료되고 컴패니언 이벤트만 생략된다.
3. 킬스위치를 켜면 열린 클라이언트도 다음 상태 확인부터 능동 개입과 기억 회상을 멈춘다.
4. 기능을 다시 켜도 비활성 기간의 업무가 소급 보상되지 않는다.
5. 브라우저가 `bond_delta=1000`, 타인의 `source_item_id`, 과거 날짜를 전송해도 반영되지 않는다.
6. 같은 업무 완료 요청이 다중 탭·네트워크 재시도로 반복되어도 서버 이벤트는 한 건이다.
7. 게스트가 로컬 관계를 쌓고 로그인한 뒤 명시적으로 이어오기를 선택한다.
8. `legacy_import` 관계는 유지되지만 계정 공통 성장에는 포함되지 않는다.
9. 로컬과 클라우드에 같은 이벤트가 있을 때 한 번만 반영된다.
10. 완료를 취소하고 다시 완료해도 추가 EXP가 없다.
11. 사용자가 기억을 삭제한 직후 같은 주제로 질문한다.
12. 삭제 후 오프라인이었던 다른 기기가 옛 기억을 업로드해도 tombstone이 복원을 막는다.
13. 원본 업무 삭제 시 미확인 파생 기억은 삭제되고 사용자가 확인한 기억은 선택 정책대로 처리된다.
14. 성장 기록만 삭제하고 관계 유지를 선택했을 때 상세 이벤트 없이 관계 스냅샷만 남는다.
15. 캐릭터 A의 관계 레벨을 올린 뒤 캐릭터 B로 바꾼다.
16. `local_only` 업무에서 파생된 내용이 클라우드 기억 후보로 전송되지 않는다.
17. Mock 항목만 있는 상태에서 브리핑·완료를 수행한다.
18. 자정·타임존 변경 직전 일일 상한을 계산한다.
19. Supabase가 실패해도 게스트/오프라인 큐가 데이터 손실 없이 유지된다.
20. Gemini 실패 시 관계·성장 사실을 꾸며내지 않는 Fallback 응답을 보여준다.

## 18. 확정 결정

2026-09-01 사용자 확인으로 D1~D4 권장안을 확정했고, 후속 요청에 따라 D5~D7 운영·신뢰·삭제 정책을 추가 확정했다.

### D1. 관계와 성장의 공유 범위

- **확정**: 관계는 캐릭터별, 사용자 성장은 계정 공통

결정 이유: 캐릭터를 바꾸는 재미는 유지하면서 실제 사용자의 성장 기록이 분산되는 것을 막을 수 있다.

### D2. 장기 기억 자동 저장 수준

- **확정**: 호칭·표현 선호만 자동 임시 저장하고, 작업 방식·약속은 사용자 확인 후 활성화

결정 이유: 초기 마찰을 낮추면서 잘못된 추론이 장기 사실로 굳는 것을 막을 수 있다.

### D3. 관계 레벨 보상의 범위

- **확정**: 캐릭터 연출·대사·기념 카드와 개인화 편의만 단계적으로 해금하고, 핵심 기능은 전 단계 공개

결정 이유: 재미는 유지하되 생산성 도구의 유용성을 사용량으로 인질 잡지 않는다.

### D4. 능동 개입 기본 강도

- **확정**: 하루 최대 2회, 집중 모드·조용한 시간에는 억제

결정 이유: 캐릭터의 존재감은 유지하면서 업무 방해와 알림 피로를 제한한다.

### D5. 시험 운영 활성화 정책

- **확정**: 테스트 기간에는 서버 롤아웃 모드와 사용자 활성화 토글을 함께 둔다.
- `pilot`의 사용자 기본값은 OFF이며 명시적 활성화 후에만 관계·기억·성장 기능을 사용한다.
- 킬스위치는 언제든 전체 실험 기능을 중단하지만 기본 AI 바리스타와 핵심 업무 기능은 유지한다.
- 비활성화는 기존 데이터를 삭제하지 않는 일시 정지이며, 재활성화 시 중단 기간을 소급 집계하지 않는다.

### D6. 이벤트 신뢰 경계

- **확정**: 로그인 사용자의 점수 이벤트는 실제 업무 mutation 또는 서버 발급 receipt를 검증한 서버만 생성한다.
- 브라우저는 `bond_delta`, 관계 단계, 성장 축, 중요도, 보상 일자를 결정할 수 없다.
- 일반 브라우저용 이벤트 직접 쓰기 API와 `companion_events` 직접 INSERT 권한을 제공하지 않는다.
- 게스트·오프라인 이벤트는 `local_provisional`이며, 서버가 원본 mutation을 확인하기 전에는 클라우드 성장으로 확정하지 않는다.
- 기존 Phase 16 로컬 관계는 사용자가 승인하면 `legacy_import`로 한 번 이어오되 계정 공통 성장에서는 제외한다.

### D7. 삭제·보존 정책

- **확정**: 기능 일시 정지, 기억 하나 삭제, 현재 캐릭터 초기화, 성장 기록 삭제, 전체 삭제를 별도 동작으로 제공한다.
- 기억 삭제 시 본문·임베딩·근거는 즉시 제거하고, 오프라인 재생성 방지용 내용 없는 tombstone만 30일 유지한다.
- 삭제는 수정·병합보다 우선하며 다른 기기의 오래된 mutation은 삭제된 데이터를 되살릴 수 없다.
- 원본 삭제만으로 관계 단계는 자동 강등하지 않지만, 사용자가 관계 초기화 또는 전체 초기화를 선택하면 제거한다.
- 상세 이벤트는 기본 180일, 에피소드는 90일, 미확인 기억 후보는 14일 보존하며 집계·확인된 기억은 사용자가 삭제할 때까지 유지한다.

## 19. 최종 수용 기준

이 설계의 도입 완료는 다음 조건을 모두 만족할 때로 정의한다.

- 관계 단계와 사용자 성장 지표가 데이터·UI·문구에서 분리된다.
- 현재 질문뿐 아니라 제한된 세션 맥락으로 후속 대화를 이어간다.
- 확인된 장기 기억을 관련 상황에서만 회상하고 사용자가 관리할 수 있다.
- 관계 상태는 검증된 이벤트 원장으로 계산되며 중복·스팸 보상이 없다.
- 로그인 사용자의 점수 이벤트는 서버 권위 근거만 사용하고 클라이언트 위조 값은 무시한다.
- 미완료·휴식·복귀가 관계 손실이나 죄책감으로 이어지지 않는다.
- 사용자 성장 카드는 근거, 표본 수, 비교 기간을 보여준다.
- 캐릭터 어조가 사실성·출처·개인정보·외부 쓰기 승인 규칙을 덮어쓰지 않는다.
- Mock·샘플·실제 연동 데이터의 출처와 성장 반영 여부가 명확하다.
- 게스트 로컬 저장, 로그인 병합, 다기기 동기화, RLS가 각각 검증된다.
- 서버 `off|shadow|pilot|on`, 사용자 토글, 킬스위치의 조합이 서버에서 일관되게 판정된다.
- 비활성 상태에서 새 기억·성장 기록·능동 개입은 멈추지만 기본 AI 바리스타와 업무 기능은 정상 동작한다.
- 삭제 범위별 데이터 처리와 보존 기간이 UI 설명·API·DB 정책에서 일치한다.
- 삭제된 기억은 즉시 검색·프롬프트에서 제외되고 오프라인 기기에서도 재생성되지 않는다.
- 정적·단위 테스트와 브라우저·모바일·로그인 E2E 결과를 구분해 보고한다.
