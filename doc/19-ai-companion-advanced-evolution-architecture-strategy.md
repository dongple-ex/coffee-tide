## 1. 비전, 범위 및 핵심 철학

CoffeeTide의 차세대 AI는 단순한 대화형 챗봇이 아니라 **사용자의 업무 리듬을 이해하고, 검증 가능한 근거로 판단하며, 사용자가 통제할 수 있는 방식으로 먼저 준비하는 인지적 업무 파트너**를 목표로 한다.

1. **Reactive to Consent-Aware Proactive**: 날씨·교통·일정·마감 신호를 조합하되 사용자의 옵트인, 조용한 시간, 빈도 제한과 근거 표시를 지킨다.
2. **Text to Safe Dynamic Action**: 모델이 코드를 생성하는 대신 등록된 인터랙티브 컴포넌트를 구조화된 의도로 선택한다.
3. **Fragmented to Verified Memory**: 대화에서 추론한 내용을 곧바로 사실로 저장하지 않고 후보·출처·신뢰도·사용자 확인을 거쳐 기억망으로 승격한다.
4. **Monolithic to Bounded Specialist Team**: 전문 에이전트는 최소 권한 도구와 명확한 입력·출력 계약 안에서만 협업한다.
5. **Cloud-First to Privacy-Aware Hybrid**: 데이터 등급과 사용자 동의를 기준으로 로컬·클라우드 처리 경로를 선택하고, 비밀번호·토큰 같은 비밀정보는 모델 입력에서 제외한다.

### 1.1 범위 밖

- 사용자의 감정·건강·업무 성과를 몰래 진단하거나 평가하지 않는다.
- 모델이 임의 JavaScript, React 컴포넌트 또는 외부 실행 명령을 생성·실행하지 않는다.
- 사용자의 승인 없이 일정 생성, 메시지 발송, 결제, 삭제 같은 외부 변경을 수행하지 않는다.
- WebGPU 실행만으로 `zero-knowledge` 또는 완전한 정보 비유출을 보장한다고 표현하지 않는다.

## 3. 6대 핵심 R&D 진화 축

### 3.1 Verified Cognitive Memory (검증형 기억 응고화와 관계 그래프)

기억 응고화는 사용자의 대화를 숨은 사실로 자동 확정하는 기능이 아니다. 이벤트와 사용자가 확인한 기억을 더 짧고 유용한 형태로 정리하는 **검증 가능한 배치 파이프라인**이다.

```text
권위 이벤트·확인된 기억
  -> 정책 필터와 tombstone 검사
  -> 후보 요약 생성
  -> 출처·신뢰도·유효기간 부착
  -> 사용자 확인 또는 제한된 자동 승격
  -> 활성 기억과 관계 그래프 반영
```

- 로그인 사용자는 서버 스케줄러가 사용자 시간대와 최근 활동량을 고려해 실행한다.
- 게스트는 브라우저가 닫힌 시각을 가정하지 않고 다음 실행 시 점진적으로 처리한다.
- 브라우저 Service Worker는 보조 동기화에만 사용하고 정확한 심야 실행을 보장하는 스케줄러로 사용하지 않는다.
- 초기 그래프는 기존 Postgres와 `item_relations`를 확장해 구현한다. 전용 그래프 DB는 실제 질의·성능 평가에서 필요성이 확인된 뒤 도입한다.
- 모든 노드와 관계는 `sourceRefs`, `confidence`, `policyVersion`, `validFrom`, `validUntil`, `userConfirmed`를 가진다.
- 사용자가 기억을 수정하거나 삭제하면 파생 요약과 관계도 함께 무효화한다.

### 3.2 Consent-Aware Proactive Intelligence (동의 기반 선제 도움)

선제 기능은 모든 신호를 계속 감시하는 방식이 아니라, 명시적으로 허용된 소스에서 이벤트가 들어왔을 때 규칙과 제한된 추론을 순차 적용한다.

- 입력 신호: 일정 시작·이동 필요 시간·업무 마감·사용자가 허용한 날씨와 교통 상태
- 필수 조건: 기능별 옵트인, 조용한 시간, 일일 상한, 중복 제거, 데이터 갱신 시각과 출처
- 기본 동작: `관찰 -> 한 줄 제안 -> 사용자 승인 -> 실행`
- 자동 실행 금지: 일정 변경, 메시지 발송, 결제, 삭제, 권한 변경
- 피드백: `도움 됨`, `지금은 불필요`, `이 유형 끄기`를 제공하고 억제 정책에 반영

예시 응답은 사실과 제안을 분리한다.

> **관찰:** 30분 뒤 외부 미팅이 있고 현재 교통 데이터가 5분 전에 갱신되었습니다.
>
> **제안:** 평소보다 10분 일찍 출발할까요? 우산 알림도 함께 설정할 수 있어요.

### 3.3 Multimodal Realtime Voice (공급자 독립 실시간 음성)

- `RealtimeVoiceProvider` 인터페이스로 공급자와 모델명을 배포 설정에서 선택한다.
- 브라우저 직접 연결은 수명이 짧고 범위가 제한된 임시 토큰만 사용한다.
- Barge-in, 네트워크 재연결, 세션 만료, 텍스트 폴백을 상태 기계로 정의한다.
- 품질은 `음성 입력 종료 -> 첫 음성 출력` 시간의 p50·p95, 연결 성공률, 중단 반응 시간으로 측정한다.
- 음성 원본 저장은 기본값 `off`이며 전사 저장도 별도 동의를 받는다.
- 음성 어조나 타이핑 속도를 스트레스·피로의 확정 신호로 저장하지 않는다. 필요한 경우 일시적인 응답 속도 조정 제안만 하고 사용자가 즉시 해제할 수 있게 한다.

참고 구현 후보인 Gemini Live API는 현재 Preview이므로 특정 모델 버전을 장기 아키텍처에 고정하지 않는다. 공식 연결 방식과 보안 조건은 [Gemini Live API](https://ai.google.dev/gemini-api/docs/live-api)를 기준으로 재검증한다.

### 3.4 Safe Generative UI & Micro-Widgets (등록형 동적 UI)

모델은 React 코드가 아니라 `WidgetIntent`만 생성한다. 서버와 클라이언트는 JSON Schema를 검증한 뒤 허용 목록에 등록된 컴포넌트만 렌더링한다.

```ts
interface WidgetIntent {
  widgetType: "exchange_calculator" | "expense_form" | "mindmap" | "timeline";
  version: number;
  props: Record<string, unknown>;
  dataRefs: string[];
  requestedActions: Array<"preview" | "save_draft" | "open_canvas">;
}
```

- 임의 JavaScript, HTML 이벤트 속성, 외부 스크립트와 임의 URL을 허용하지 않는다.
- 위젯은 기본적으로 읽기 또는 미리보기 권한만 가진다.
- 외부 데이터 변경은 기존 승인 토큰과 멱등성 경계를 재사용한다.
- 환율·비용·일정처럼 계산 정확도가 중요한 위젯은 결정적 함수와 단위 테스트를 사용한다.
- 캔버스 동기화는 블록 ID·버전·작성 주체를 기록하고 충돌 시 사용자가 선택하게 한다.

### 3.5 Bounded Specialist Orchestration (제한된 전문가 분업)

12종 바리스타는 사용자 경험과 말투를 담당하고, 백그라운드 전문가는 검증된 능력 목록 안에서만 작업한다.

| 전문가 | 기본 권한 | 주요 출력 |
|---|---|---|
| Research Reader | 승인된 웹·사내 자료 읽기 | 출처가 연결된 조사 노트 |
| Finance Analyst | ECOS·비용 데이터 읽기, 결정적 계산 | 계산식·통화·기준시각이 있는 분석 |
| Schedule Planner | 캘린더 읽기, 변경 초안 작성 | 충돌과 이동 시간을 포함한 제안 |
| Safety & Evidence Check | 실행 계획과 근거 읽기 | 정책 위반·근거 부족·민감정보 경고 |

- Orchestrator 한 곳만 사용자에게 최종 응답하고 에이전트 간 무한 위임을 금지한다.
- 각 실행은 `runId`, 목적, 입력 참조, 권한, 비용·시간 한도, 도구 결과, 실패 원인을 기록한다.
- 전문가는 사용자 권한을 확대하거나 다른 전문가에게 자격 증명을 전달할 수 없다.
- Safety Agent는 보조 검수자이며 인증·RLS·승인 토큰 같은 결정적 통제를 대체하지 않는다.
- 읽기, 초안, 외부 변경을 분리하고 외부 변경은 언제나 사용자 승인 후 단일 실행기로 보낸다.

### 3.6 Privacy-Aware Hybrid Inference (데이터 등급 기반 로컬·클라우드 라우팅)

WebGPU 또는 WebLLM은 선택 가능한 처리 수단이며 그 자체가 보안 경계나 zero-knowledge 보장은 아니다. 라우터는 데이터 등급, 기기 지원 여부, 모델 정책과 사용자의 명시적 선택으로 경로를 결정한다.

| 등급 | 예시 | 처리 원칙 |
|---|---|---|
| `prohibited` | 비밀번호, 인증 토큰, 비밀 키 | 로컬·클라우드 모델 모두 입력 금지 |
| `local_only` | 개인 일기, 급여 상세, 사적 약속 | 지원 기기에서 로컬 처리, 미지원 시 기능 중단 또는 명시적 재선택 |
| `cloud_private` | 일반 업무 문서, 회의록 | 암호화 전송, 최소 범위, 보존 정책 적용 |
| `cloud_allowed` | 사용자가 공개·외부 검색을 허용한 내용 | 목적과 공급자를 표시하고 처리 |

- 라우팅 전 원문과 첨부에서 비밀 패턴을 탐지하고 차단한다.
- 로컬 처리 결과도 로그·캐시·동기화 과정에서 클라우드로 전출되지 않는지 별도로 검사한다.
- 민감도 판정이 모호하면 더 제한적인 등급을 선택하고 사용자에게 이유와 선택지를 보여준다.
- WebGPU 보안·프라이버시 제약은 [W3C WebGPU 사양](https://www.w3.org/TR/webgpu/)을 기준으로 지원 범위를 갱신한다.

## 4. Phase 19-0 선행 안전 게이트

새로운 기억·선제 알림·에이전트를 추가하기 전에 현재 Phase 17 구현과 설계 정본의 차이를 닫는다. 이 단계가 완료되지 않으면 Phase 19-A 이후 기능은 `off`를 유지한다.

| 영역 | 필수 조치 | 통과 조건 |
|---|---|---|
| 사용자 식별 | API body·query의 `userId` 제거, Supabase `auth.getUser()` 결과만 사용 | 다른 사용자 ID를 주입한 모든 요청이 401/403 또는 소유권 오류 |
| 서버 권위 | 서비스 역할 사용 전 인증·소유권 재검증, 일반 조회는 사용자 세션 클라이언트 사용 | 서비스 역할 키가 있어도 교차 사용자 접근 불가 |
| 기능 게이트 | 서버 모드·킬스위치·코호트·사용자 토글을 모든 읽기·쓰기 API에 동일 적용 | `off`와 킬스위치에서 DB 읽기·쓰기 0건 |
| 이벤트 원장 | `source_item_id`를 실제 업무 ID 형식과 통일, 이벤트+프로필 갱신을 원자적 RPC로 처리 | 중복·재시도·다중 탭에서도 EXP 단일 반영 |
| 삭제 | 확인 토큰 검증, 실제 범위 삭제, tombstone 생성, 재조회 검증 | 삭제 완료 응답 후 본문·파생 데이터 0건, tombstone만 정책 기간 유지 |
| 오류 처리 | 저장 실패를 성공이나 빈 기본값으로 숨기지 않고 구조화된 오류 반환 | 운영 로그에서 실패 원인·runId 추적 가능 |
| 평가 기반 | 인증·RLS·삭제·멱등성·오프라인 복구 테스트 추가 | 자동 테스트와 인증된 원격 E2E 모두 통과 |

## 5. 공통 계약과 신뢰 경계

### 5.1 사용자 신원

```text
Browser request
  -> CoffeeTide session check
  -> Supabase authenticated user
  -> server-owned userId
  -> ownership/RLS check
  -> repository or privileged RPC
```

- 클라이언트는 `userId`, `authority`, 성장 점수, 승인 상태를 확정할 수 없다.
- 게스트 데이터는 `guest`라는 공용 서버 사용자가 아니라 기기 로컬 namespace에 보관한다.
- 로그인 병합은 사용자가 범위와 중복 처리 결과를 확인한 뒤 한 번만 실행한다.

### 5.2 실행 권한

| 등급 | 예시 | 정책 |
|---|---|---|
| `read` | 일정·업무·환율 조회 | 허용 소스와 최소 필드만 읽기 |
| `draft` | 일정·답장·보고서 초안 | 외부 변경 없이 미리보기 생성 |
| `write` | 일정 생성·파일 저장 | 사용자 승인 토큰과 멱등 키 필요 |
| `destructive` | 삭제·권한 변경 | 별도 재확인, 범위 표시, 완료 검증 필요 |

### 5.3 핵심 도메인 계약

```ts
interface EvidenceRef {
  sourceType: string;
  sourceId: string;
  observedAt: number;
  freshnessSeconds?: number;
}

interface ProactiveCandidate {
  id: string;
  reason: string;
  evidence: EvidenceRef[];
  urgency: "low" | "medium" | "high";
  expiresAt: number;
  proposedAction?: "open" | "draft" | "remind";
}

interface SpecialistRun {
  runId: string;
  specialist: "research" | "finance" | "schedule" | "safety";
  capability: string;
  inputRefs: EvidenceRef[];
  maxDurationMs: number;
  maxCostUnits: number;
  status: "planned" | "running" | "succeeded" | "failed" | "cancelled";
}
```

원문 전체를 에이전트 사이에서 복사하지 않고 참조와 필요한 최소 필드만 전달한다. 최종 답변은 사용한 근거, 갱신 시각, 불확실성과 실행 여부를 표시한다.

## 6. 단계별 도입 로드맵

일정은 Phase 19-0 완료 시점에 다시 산정하며 아래 분기는 목표 순서다. 각 단계는 `off -> shadow -> internal pilot -> opt-in pilot -> on`으로 승격하고 독립 킬스위치를 가진다.

| 단계 | 목표 시기 | 주요 산출물 | 승격 게이트 |
|---|:---:|---|---|
| **Phase 19-0** | 2026 Q3~Q4 | 인증·RLS·이벤트·삭제 하드닝, 평가 하네스 | 보안·삭제·멱등성 테스트와 인증 E2E 통과 |
| **Phase 19-A** | 2026 Q4 | 규칙 우선 선제 알림, 등록형 위젯 3~5종, 캔버스 버전 동기화 | 원치 않는 알림·오류·승인 우회 기준 충족 |
| **Phase 19-B** | 2027 Q1 | 기억 후보 응고화, 출처 기반 관계 그래프, 수정·삭제 전파 | 확인 정확도·수정률·삭제 전파·회상 근거 기준 충족 |
| **Phase 19-C** | 2027 Q1~Q2 | 공급자 독립 실시간 음성, Barge-in, 텍스트 폴백 | 모바일 네트워크 TTFA·연결률·중단 반응 기준 충족 |
| **Phase 19-D** | 2027 Q2 | 제한된 전문가 오케스트레이션, 데이터 등급 기반 하이브리드 추론 | 무권한 실행 차단, 비용·시간 한도, 감사·취소·복구 검증 |

각 단계는 앞 단계의 기반을 재사용하지만 하나의 대규모 릴리스로 묶지 않는다. 선제 알림, 기억 응고화, 음성, 전문가 분업, 로컬 추론을 각각 독립적으로 중단할 수 있어야 한다.

## 7. 측정과 평가

절대 수치를 먼저 약속하지 않는다. `shadow` 단계에서 최소 2주간 기준선을 수집한 뒤 제품 목표를 확정한다.

| 영역 | 핵심 지표 | 실패·안전 지표 |
|---|---|---|
| 선제 도움 | 제안 열람률, 수락률, 실제 행동까지 걸린 시간 | 무시율, 유형 끄기, 일일 상한 초과, 오래된 데이터 사용 |
| 동적 UI | 위젯 완료율, 텍스트 대비 단계 감소 | Schema 거절률, 렌더 실패, 승인 없는 외부 변경 |
| 기억 | 사용자 확인 정확도, 근거 회상률, 반복 질문 감소 | 수정률, 잘못된 회상, 삭제 후 재생성, 민감정보 후보화 |
| 음성 | TTFA p50·p95, 연결 성공률, Barge-in 반응 | 원치 않는 녹음, 세션 누수, 텍스트 폴백 실패 |
| 전문가 | 업무 성공률, 근거 충족률, 평균 비용·시간 | 도구 오류, 순환 위임, 권한 초과, 예산 초과 |
| 프라이버시 | 등급 판정 정확도, 로컬 처리 성공률 | 금지정보 모델 입력, 라우팅 불일치, 로그·캐시 유출 |

평가 세트는 정상 흐름뿐 아니라 프롬프트 인젝션, 타 사용자 ID 주입, 중복 요청, 오래된 오프라인 큐, 공급자 장애, 네트워크 단절, 잘못된 교통 정보와 모델 환각을 포함한다.

## 8. 제품 차별화 가설

경쟁 제품의 기능을 근거 없이 축소 비교하지 않는다. CoffeeTide가 검증할 차별화 가설은 다음 세 가지다.

1. **업무 정본과 연결된 관계성**: 친근한 페르소나가 단순 사용량이 아니라 검증된 업무 실행과 회고를 바탕으로 관계를 형성하면 지속 사용에 도움이 되는가.
2. **근거가 보이는 선제 도움**: 데이터 출처와 판단 이유를 한 줄로 보여주면 사용자가 알림을 방해가 아니라 도움으로 받아들이는가.
3. **대화에서 실행까지 이어지는 UI**: 등록형 위젯과 캔버스가 텍스트 답변보다 실제 업무 완료 단계를 줄이는가.

경쟁 비교가 필요하면 별도 시장 분석 문서에서 제품 버전, 조사일, 출처, 동일 시나리오와 측정 결과를 기록한다.

## 9. 결정이 필요한 사항

| 결정 | 권장안 | 이유 |
|---|---|---|
| Phase 19의 첫 사용자 가치 | 선제 알림 + 등록형 위젯 | 기존 데이터·캔버스를 재사용하며 효과 측정이 빠름 |
| 기억 자동 승격 | 정상 선호만 제한적으로 허용하고 나머지는 사용자 확인 | 잘못된 암묵 지식 고착 방지 |
| 외부 변경 기본값 | 제안·초안까지만 자동, 쓰기는 매번 승인 | 신뢰와 복구 가능성 확보 |
| 감정 신호 | 초기 범위에서 제외 | 민감도·오탐·설명 책임 대비 핵심 가치가 낮음 |
| 전용 그래프 DB | 초기에는 도입하지 않음 | 현재 Postgres 관계 모델로 가설 검증 가능 |
| 로컬 AI 미지원 기기 | 클라우드 자동 전환 금지, 사용자 재선택 | 민감정보의 묵시적 외부 전송 방지 |

## 10. 완료 정의

Phase 19 전략은 다음 조건을 충족할 때 `정본`으로 승격한다.

- Phase 19-0의 인증·삭제·이벤트 원장 문제가 코드와 원격 환경에서 검증된다.
- 각 기능의 데이터 입력, 권한, 보존, 삭제, 실패·폴백 계약이 문서화된다.
- 제품 지표와 안전 지표의 기준선 및 파일럿 목표가 승인된다.
- 공급자 장애·비용 초과·오탐 증가 시 사용할 기능별 킬스위치와 롤백 절차가 준비된다.
- 모바일, 게스트, 로그인, 다기기, 오프라인, 실제 외부 연동 테스트 매트릭스가 승인된다.
